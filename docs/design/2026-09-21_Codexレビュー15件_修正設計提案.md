### 3.3 正常処理と中断回復

1. Webhookは生本文の署名を検証後、必要最小のIDと状態を永続化する。重複でも「IDが存在する」だけでは完了にしない。
2. サーバーは利用者単位の処理権をDBで取得し、その後にStripeの現在状態を取得する。DBトランザクションを開いたままHTTP通信しない。
3. DBへの反映とイベント完了は一つのDB関数・一つのトランザクションで確定。処理所有者token、期限、世代番号、対応する利用者/Customer/契約、更新行数を検証する。
4. 期限が切れた処理は別実行が引き継げる。古い実行結果はtoken/世代不一致でDB反映を拒否する。
5. **DBの古い書き込み拒否だけでは、既に送ったStripe操作を取り消せない。** POST作成の同一操作には同じ冪等キーを使い、タイムアウト後もその操作の結果を照合する。結果不明の旧Checkout作成がある間に別キーで作り直さない。
6. API・DB障害はretryへ。紐付け不明・複数の有効契約など自動決定できないものはneeds_reviewへ。未解決をprocessed/ignoredで隠さない。
7. 退会要求済みは、新Checkout・resumeを新たに開始できない。Checkout発行直前・結果保存前も要求状態を確認し、発行競合で残ったSessionを失効処理へ送る。

Customer作成も外部呼び出し前に操作を記録し、Customer用とSession用の冪等キーを分ける。同じキーには同じパラメータを送る。Stripeのキー保持期間経過後に結果不明の作成要求を無条件に再送せず、照合できなければneeds_reviewへ送る。DELETEの契約停止は冪等キーに頼らず現在状態を照合する。結果不明の先行操作がある間は、処理権の期限が切れても逆向きの操作を始めない。[Stripeの冪等リクエスト](https://docs.stripe.com/api/idempotent_requests)

処理権の引き継ぎ番号と契約世代は別の値として扱う。既存契約は照合して世代0に登録し、新しいCheckoutとsubscription_dataのmetadataにはサーバーで確定した操作ID・契約世代を付ける。metadata単独を所有権の証明にしない。

### 3.4 再試行を実際に動かす条件

- 「後でworkerを作る」として受信だけ200に変えてはいけない。**永続受信後200を返す方式と再実行workerを同時に完成させる。** それまでは同期処理の失敗を5xxとしてStripe再送を残す。
- 提案名`billing-reconcile`のサーバー専用処理で、期限切れprocessing・retry・退会処理中を回収する。既存Supabase内で定期起動し、認証付きの管理者再実行も用意する。
- 定期起動の具体手段（Supabaseの利用可能なCron/HTTP実行機能、シークレット保管方法）は環境確認後に確定する。DBに平文キーを書かない。外部サービス・依存追加が必要なら別提案。**自動起動・失敗可視化の実証がなければ本番受入不可。**
- 最終試行時刻・次回試行・未解決件数を既存管理画面で見られるようにする。ログには原文・メール・秘密値を出さない。
- Stripe再送期限を過ぎても、保存した対象IDによる現状態照合で復旧できるようにする。イベントAPIで過去本文を取得できる期間だけに依存しない。

### R03 — 古い通知で状態・契約を巻き戻さない

**変更候補:** stripe-webhook、checkout/cancelの反映経路、billing-control系RPC、期限掃除関数。契約対応と管理用操作記録。

**受入条件:** 古いpast_due→新active／新active→古いpast_due、同秒通知、旧契約active後着、新契約終了、解約と同期の競合、古い処理の遅延応答を確認。**単に再取得を1回挟むだけでは合格にしない。**

### 検証の実行方針

- 既存の93件成功、型検査3件、Lint成功は前回レビュー時の記録。新しいコードには必要な範囲の検査を実施する。
- shared変更: sharedテストと型検査。mobile/admin変更: 対象の型検査とLint。権限/関数変更: SQLスイートとサービスAPIの正常・異常系。
- Edge Functionsはtscだけで検証済みにしない。Deno/ローカルEdge Runtimeで実際の応答を確認する。環境がない場合はスタブ試験と実行未確認を区別し、依存やDenoを無断追加しない。
- migrationは新規ファイルにし、ローカル適用は`pnpm exec supabase migration up`。`db reset`を使わない。型再生成とschema snapshot更新をセットにし、生成コマンドはREADME/既存運用から確認する。
- 実Stripe/Agoraはテスト環境で最後に確認。キー未設定なら他の実装・合成データ検証は進められるが、実サービス疎通を完了扱いにしない。
- 全体の必須検査例は既存の`pnpm run lint`、各パッケージの`tsc --noEmit`、`pnpm -F @hapimari/shared test`、`bash scripts/run_sql_tests.sh`。Windowsではプロジェクト指定のPATH補正を行う。
- 検証をユーザーに依頼する場合、作業ディレクトリ移動を含むPowerShellの1回コピーで完結するコマンドを担当者が用意する。未作成のテストコマンドを既存コマンドとして渡さない。

## 6. オーナーが確認する画面上の結果

テスト環境とテストユーザーの用意は実装担当が行う。秘密キーやパスワードのチャット共有は不要。

| 操作 | 正しい結果 | エラーになるべき場合 |
|---|---|---|

匿名化は画面だけで判定できないため、担当者が合成データの「対象列が消えた/残す特徴量は不変」という件数・成否を提示する。原文や個人情報を確認用ファイルへ書き出さない。

## 7. 変更範囲・権限・残リスク

| 領域 | 誰が何をできるようになるか / できなくなるか | 土台の判断 |
|---|---|---|
| 決済・退会 | 本人は退会処理状況を確認。運営は未解決処理の分類/再実行。利用者は契約状態・処理完了を直接変更できない | 永続処理状態・契約対応・再実行責任。外部キュー案との比較は§3 |
| 写真・ブロック | 非在籍者の他者写真閲覧、第三者のブロック関係照会を禁止。本人の必要な操作は維持 | 公開/内部関数の境界。関数の単純削除は非推奨 |
| 匿名化 | 利用者・運営とも、消去対象の自由文を90日後に復元できなくなる | 保持目的と消去対象。既存行補修は不可逆なため別途実行承認 |
| 一覧・検索 | 本人は表示対象の全ページへ到達。位置情報・生年月日の取得範囲は拡大しない | サーバーでの表示日/順位計算とカーソル。無制限全件返却は非推奨 |

総合リスクは**高**。認証方式そのものは変更しないが、決済・RLS・個人情報・通話・マッチング・管理画面に触れる。設計段階(A)で課金停止/再実行/公開権限を、公開前(C)でStripeテスト環境とAPI経由のアクセス制御を専門家に確認してもらう。

戻し方は段階ごとに準備する。機能無効化・新規受付停止で安全側に止める方法を先に定義し、古い公開RPCや課金迂回経路を再開するロールバックはしない。削除済み自由文は戻せない。新規テーブルを即DROPして処理中の状態を失わない。
