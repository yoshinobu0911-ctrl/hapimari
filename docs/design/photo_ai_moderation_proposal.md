# 設計提案: 写真AIモデレーションの導入（人力＋AI併用）

> tasks.md「写真のAIモデレーション導入」（オーナー方針: 人力＋AIのハイブリッド）に対する設計提案。
> CLAUDE.md §4 に基づき、承認前は未実装。センシティブ領域（写真・個人情報）のためリスク「高」＝明示承認まで着手しない。

## 1. 目的
現在、写真審査は完全に人力（オーナー1名が管理画面 `/photos` で目視）。差し込み口 `apps/admin/lib/photo-ai.ts` の `analyzePhoto` は常に `null` を返すスタブで、AI判定は未実装。オーナー方針どおり、AI判定を審査キューに**参考情報として並記**し、目視の負担と見落としリスクを減らす。

## 2. 変更範囲（規模: S〜M）
- `apps/admin/lib/photo-ai.ts` — `analyzePhoto` の実装（外部API呼び出し）
- `apps/admin/app/photos/page.tsx` — 審査キューにAI判定バッジ（ok / ng / unsure）を表示
- `.env.example`（admin）— `PHOTO_MODERATION_API_KEY` を追記
- 新規依存パッケージ: **なし**（後述Aの場合。fetchで完結）

## 3. 設計方針（プロバイダ選択）

| 選択肢 | 概要 | 契約の重さ | 費用目安 |
|---|---|---|---|
| **A（推奨）OpenAI omni-moderation** | 画像入力対応のモデレーションAPI | OpenAIのAPIキー1つ | 現行は無料枠あり（要最新確認） |
| B AWS Rekognition | 画像特化・精度に定評 | AWSアカウント契約が別途必要 | 従量課金 |
| C Google Vision SafeSearch | 同種の画像判定API | GCPアカウント契約が別途必要 | 従量課金 |

**推奨: A**。理由は契約・実装コストの軽さ（キー1つ・SDK不要でfetch呼び出しのみ）。精度に不安が出れば、`analyzePhoto` はプロバイダ非依存の型（`AiPhotoVerdict`）で設計済みなので、後からB/Cへ差し替え可能。

- 判定は**あくまで参考表示**。`ng`/`unsure` でも自動却下はせず、最終承認は今までどおり人力（オーナー）が行う。これは変更しない。
- API障害・未設定時は `null` を返し人力のみにフォールバック（既存の設計をそのまま維持）。

## 4. リスクレベル
**高**（CLAUDE.md §6: 写真・書類アップロードはセンシティブ領域）。オーナーの明示的な「OK」まで実装しない。

## 5. リスク・副作用
- **第三者への画像送信**: 審査対象の写真URLを外部API（OpenAI等）に送ることになる。プライバシーポリシー（`docs/legal/`）に「第三者提供」「業務委託先」としての記載が必要か、行政書士面談時に合わせて確認することを推奨。
- **データ利用規約の確認**: OpenAIの場合、モデレーション目的で送信した画像がモデル学習に使われないか利用規約で要確認（要オーナー確認 or 次回リサーチ）。
- **費用**: 現状は無料枠想定だが、会員数・写真枚数が増えると課金が発生する可能性があるため、契約前に最新の料金体系を確認。
- **誤判定**: `ng`/`unsure` 判定を過信すると健全な写真を不当に止める恐れがある。表示はあくまで「参考バッジ」とし、最終判断ボタン（承認/却下）の挙動は変えない。

## 6. 動作確認方法（非エンジニア向け）
1. 管理画面 `/photos` を開く
2. 新規アップロード写真の審査行に「AI判定: ok / ng / unsure」のバッジが表示されることを確認
3. テスト用に用意した不適切画像（ダミー）で `ng` バッジが出ることを確認
4. `ng` 判定でも「承認」ボタンで通常どおり人力承認できる（自動却下されない）ことを確認

## 7. 確認質問（最大3つ）
1. プロバイダはA（OpenAI）でよいか、精度重視でB/C（AWS/Google・要アカウント契約）を検討するか
2. プライバシーポリシーへの追記要否は、行政書士面談（届出の件）と合わせて確認する運びでよいか
3. 月額の予算感の目安はあるか（現状は無料枠内想定で進めてよいか）
