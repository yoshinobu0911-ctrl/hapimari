# M6.7 受け入れ記録: 退会データの保持方針（90日で匿名化）

> オーナー決定（2026-07-30）:
> ・退会後90日は全情報を保持 → 90日経過で**個人を特定できる情報をすべて削除**し、
>   アルゴリズム学習用の**特徴量だけ**を匿名IDのまま無期限保持（**写真も削除**）
> ・メールアドレスは**ハッシュ値のみ無期限保持**（配信除外・再登録禁止・ブロック引き継ぎ）
> ・再登録は**退会から7日後**より可（新規アカウント扱い・過去データは復元しない）
>
> 検証: `docker exec -i supabase_db_hapimari psql -U postgres -d postgres < scripts/test_m67_retention.sql`

## 設計の要点

| 論点 | 採用した設計 | 理由 |
|---|---|---|
| 学習データの残し方 | profiles の行は消さず、**個人特定列を消して特徴量列へ変換** | 行を消すとマッチ・デート・通話の関係が壊れ、学習データが失われる |
| 匿名性の担保 | **メールハッシュ台帳と特徴量レコードを相互に紐付けない** | 紐付けると「メールを知っていれば特徴量を再特定できる」ため匿名化が崩れる |
| 再登録の実現 | 退会時に**認証アカウントのメールを無効値へ置換**して解放 | 同じアドレスで新規登録できる＝常に新規アカウント扱いになり、過去データが復活しない |
| 7日の弱点補償 | **通報履歴をハッシュで引き継ぐ**／ブロック関係も引き継ぐ | 「退会→即再登録で通報リセット」という悪用が成立しなくなる |
| 写真・書類の実削除 | DBは削除待ちキューに積み、**管理画面のジョブが Storage API で実削除** | Supabaseは SQL からの storage 直接DELETEを禁止している |

## 検証中に発見して修正した不具合

**プロフィールから外した写真がストレージに残り、削除対象から漏れていた。**
当初の実装は `photo_urls` に載っているパスだけをキューに入れていたため、
利用者が一度アップロードして後から削除した写真が永久に残る状態だった。
**そのユーザーのフォルダ配下すべて**を対象にするよう修正し、実削除まで再確認した。
