## 1. 目的

「お相手からのいいね」画面（`apps/mobile/src/app/(tabs)/likes.tsx`）は、受信いいねを**全件**取ってから画面側で表示日（R4 の1日100件繰越）を割り当てている。PostgREST の `max_rows=1000` で結果が無言で打ち切られるため、受信が1000件を超えると次の2つが壊れる。

1. 昇順で取っているため、**新しい側（1001件目以降）が欠ける**。新着のいいねが画面に出ない。
2. 繰越件数（「ほかに N 件…明日以降に表示されます」）が、欠けた後の件数で計算されて**過小**になる。

表示日の割当を DB 側で全件に対して行い、そのあとで新しい順にページ化して返す RPC に置き換える。

## 3. 設計方針

### 3.1 RPC の仕様

```
get_received_likes_page(p_before_created_at timestamptz = null, p_before_id uuid = null, p_limit int = 50)
returns table (like_id uuid, from_user uuid, message text, created_at timestamptz,
               display_date date, carried_over_count int)
```

- **SECURITY INVOKER・search_path=public・stable**。likes の既存 RLS（自分が送った/もらった行のみ）がそのまま効く。加えて関数内で `to_user = auth.uid()` に限定（引数で受信者を指定させない）。
- **対象の絞り込み（割当より前）**: 送り主が `profiles_public` に見える人だけ（＝現行画面と同じ。閲覧者が在籍中・送り主が active・ブロックなし）。現行は「絞り込み後に割当」なので順序を変えない。
- **表示日の割当**: `like_visibility.ts` の `assignVisibleDates` と同じアルゴリズムを plpgsql で1行ずつ再現する。
  - 並び: `created_at` 昇順（NULL は先頭。TS の `''` と同じ）、同時刻は `id` 昇順で安定化（TS は同時刻の順序が未定義だったので、安定化は仕様の明確化であり挙動の変化ではない）。
  - JST の暦日: `(created_at at time zone 'Asia/Tokyo')::date`（TS の +9 時間と同じ。日本に夏時間は無い）。created_at が NULL のときは「今日」。
  - 上限: 受信者が女性なら 100（`FEMALE_DAILY_LIKE_LIMIT` と同じ値を SQL に定数で書く。SQL テストで固定）、それ以外は無制限。
- **ページ化**: 表示対象（display_date ≦ 今日）を**新しい順**（created_at 降順、同時刻は id 降順）に並べ、カーソル `(p_before_created_at, p_before_id)` より後ろを `p_limit` 件返す。`p_limit` は 1〜100 に丸める（既定 50）。
- **繰越件数** `carried_over_count` は、ページに関係なく**全体の**繰越件数（display_date > 今日）を各行に同じ値で載せる。
- 未ログイン（`auth.uid()` が NULL）は0行。

### 3.2 画面

- `useInfiniteQuery`（React Query の継続取得）で1ページ50件ずつ取る。次ページのカーソルは最終行の `(created_at, like_id)`。50件未満なら終わり。
- 各ページの送り主プロフィールは、そのページの送り主ID（最大50件）だけ `profiles_public` から取る（現行と同じ取り方。URL 長の問題も消える）。
- 一覧の末尾に「さらに表示」ボタン（次ページがあるときだけ）。
- Realtime の新着通知で `['received-likes', myId]` を無効化すると、全ページを取り直す（現行と同じキー）。

### 3.3 判断が分かれる点（夜間は推奨案で進める）

| # | 論点 | A（推奨・採用） | B | 理由 |
|---|---|---|---|---|
| 1 | 割当の場所 | DB 側で毎回全件を割当（永続列を持たない） | 表示日を likes の列に保存 | 旧提案 R12 も A。列を持つとブロック・退会で対象が変わるたびに再計算が要り、スキーマ変更（センシティブ）にもなる。会員規模では毎回計算で足りる |
| 2 | 送り主プロフィールの取得 | 画面がページごとに `profiles_public` から取る | RPC がプロフィール列も返す | 公開範囲の判定（写真の可視判定を含む）を `profiles_public` の1か所に保つ。RPC に公開列を並べると二重管理になる |
| 3 | ページ送り | 「さらに表示」ボタン | スクロール末尾で自動取得 | 現行が ScrollView。FlatList への書き換えは変更が大きい。中高年向けに明示ボタンの方が分かりやすい |
| 4 | 100 の定数 | SQL に直書きし、SQL テストで TS の定数値と同じ 100 を固定 | 設定表を新設 | 依存・スキーマを増やさない。変更時は migration とテストで気づける |

## 4. リスクレベル: **高**

マッチング・いいね（憲法 §6）と、権限（新しい RPC）に触れるため。技術的には読み取り専用の関数1本と画面の取得方法の変更。

## 5. リスク・副作用

- **性能**: 1回の呼び出しで受信いいねを全件走査する（O(n)）。`idx_likes_to_user_created` を使う。数千件規模なら問題ないが、大規模での EXPLAIN は未測定（I12 と同じく会員増加後に実測）。
- **表示の同一性**: 1000件以下では現行と同じ件・同じ順・同じ繰越件数になる（同時刻の並びだけ id で安定化）。
- **ページ間の整合**: 取得途中に新着が来ても、カーソルより古い側は変わらない（新着は Realtime の無効化で先頭から取り直す）。ブロック等で対象が変わった場合も、無効化で全ページを取り直す。
- **反映の順序**: DB（migration）が先、アプリ配信が後（関数が無い DB に新アプリがつながると一覧が読み込みエラーになる）。

## 6. 動作確認方法

- オーナー: Web 版で「お相手から」タブを開き、いいねが今までどおり新しい順に出ること。
