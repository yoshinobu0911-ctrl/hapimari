## 受け入れ条件（SPEC §6 M4 / 設計書 §2.3）

1. 10往復（20通）で双方に打診UIが出る
2. 片方拒否時に相手へ通知が出ない（R6）
3. 双方合意 → 日程確定まで通る
4. 翌日フィードバック入力までE2Eで通る

## 補足・既知の制限（委託エンジニア向け）

1. **ローカル通知は「承諾した側」のみ予約される**（提案者側は確定を自動メッセージで知るため画面を開いた時にアプリ内バナーで代替）。Webはローカル通知非対応のためアプリ内バナーのみ（設計書どおり）。
2. SPECのM4記載「Edge Function」は **Postgres RPC（security definer）で代替**（M3のQ&Aで確立した方針。低レイテンシ・デプロイ物の削減。検証ロジックはすべてサーバ側にある）。
3. 相手側への状態伝搬は自動メッセージ（既存Realtime）便乗方式。date_proposals自体のRealtime配信はRLS遮断のため行っていない（承認済み判断#1）。
4. レビュー観点: migration のRPC群（当事者検証・R6マスク・存在秘匿）と `uniq_active_date_proposal` の部分uniqueが最重要。3段階レビューB（MVP完成時）の対象。
