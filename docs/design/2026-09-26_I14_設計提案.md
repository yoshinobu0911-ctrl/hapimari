## 1. 目的

「さがす」画面の年齢の絞り込みは、`profiles_public` ビューの `age` 列（`date_part('year', age(birth_date))` で毎回計算）に `gte/lte` をかけている（`apps/mobile/src/lib/discover-query.ts:36-37`）。計算式への条件なので、用意済みの索引 `idx_profiles_status_gender_birth (status, gender, birth_date)` を使えず、会員が増えると全件の年齢を計算して比べることになる（統合表 I14）。

年齢の範囲を「生年月日の範囲」に変換して DB 内で絞り、索引を使えるようにする。生年月日そのものは画面へ返さない。

## 2. 現状の事実（2026-09-26 確認）

| 事実 | 根拠 |
|---|---|
| 検索は PostgREST でビュー `profiles_public` を直接絞っている | `discover-query.ts:30-44` |
| ビューは `birth_date` を公開せず、`age` だけを出す | `schema.generated.sql` の profiles_public 定義 |
| 索引 `(status, gender, birth_date)` はすでにある | `schema.generated.sql` の `idx_profiles_status_gender_birth` |
| PostgREST の絞り込みはビューの列にしかかけられない。生年月日を列として出さずに生年月日の範囲で絞る手段は、検索用の RPC を作ること | PostgREST の仕様（計算列の関数は追加の引数を取れない） |
| 現在のローカルの会員数は 21人。性能差は計測できない規模 | ローカル DB |

## 3. 設計方針

### 3.1 実現方法（どちらも「検索 RPC」が必要）

年齢 a 歳以上 ⇔ 生年月日 ≦ 今日 − a 年、年齢 b 歳以下 ⇔ 生年月日 > 今日 − (b+1) 年（JST の今日で計算）。この変換を DB 内で行い、`status='active' and gender=… and birth_date between …` で索引を使う。

```
search_profiles(p_age_min int, p_age_max int, p_prefectures text[], p_marital text[],
                p_intents text[], p_times text[], p_limit int)
  returns setof profiles_public   -- 返す列はビューと同じ。birth_date は返さない
```

- SECURITY INVOKER で内部は `profiles_public` を id で引き直す（公開範囲の判定をビューに一元化したまま）か、DEFINER で profiles を直接読んでビューと同じ条件を書く（性能は良いが公開条件が2か所になる）。
- 画面側 `buildDiscoverQuery` をこの RPC 呼び出しに置き換える。

### 3.2 判断が分かれる点（オーナーに決めてほしい）

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A | I14 だけ先に `search_profiles`（年齢＋既存の絞り込み）を作る | 年齢の絞り込みがすぐ索引を使える | I30（距離で絞ってから並べる検索 RPC）で**同じ関数を作り直す**ことになり、二度手間・二度のレビュー |
| **B（推奨）** | I14 を I30 の検索 RPC にまとめ、別フェーズで一度に作る | 検索の作り直しが1回で済む。公開条件・距離の保護・ページ化を一度に設計できる | 会員が増えるまで今の方式のまま（21人規模では差は出ない） |

推奨 B の理由: 現在の規模では性能差が無く、I30 と I14 はどちらも「検索を DB 関数に移す」同じ作業のため。オーナー注記「会員が増えるまで見送りでもよい」（I12/I13/I16）とも整合する。
