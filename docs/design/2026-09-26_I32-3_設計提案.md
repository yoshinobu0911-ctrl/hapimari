# I32③ 通話トークン再発行による上限延長の防止（通話開始時刻のサーバー管理）設計提案（2026-09-26）

> 状態: **承認待ち（文書のみ。コード・DB は変更していない）**。
> 夜間作業では実装しなかった。理由: 「掛け直したときに残り時間をどう扱うか」という**利用者体験の判断**が設計の中心にあり（下記 3.2）、オーナー決定（2026-09-24 §I32）に書かれていないため（夜間指示書 §3「設計提案に書かれていない判断が必要な項目は推測で進めない」）。また Agora の実キーが無く、実際の通話で切断タイミングを確かめられない。
> 作成: Claude Opus 5.5（夜間自律作業）。人間レビューの段階: (A) 設計段階。

## 1. 目的

通話の上限（1回30分）は現在、①画面のタイマー（1800秒）と、②`agora-token` が発行するトークンの有効期限（1860秒＝30分＋猶予1分）で守っている。しかし `agora-token` は呼ばれるたびに**新しい31分のトークン**を出すため、改造したアプリでトークンを取り直して入り直せば、30分を超えて話し続けられる（Grok#3・統合表 I32）。

通話の開始時刻をサーバー側で持ち、**同じ通話の間は残り時間分のトークンしか出さない**ようにする。

## 3. 設計方針

### 3.1 共通部分

- セッションはマッチごとに1つ。`agora-token` は service_role で `call_sessions` を読み書きする（利用者のアプリからは触れない）。
- 開いているセッション（`ended_at is null` かつ `expires_at > now()`）があれば、`ttl = expires_at - now()` のトークンを出す（取り直しても期限は延びない）。発信側・着信側とも同じセッションを使う。
- 無ければ `started_at = now()`、`expires_at = now() + 1860秒` で作る。
- 残り時間が60秒未満なら新しいトークンを出さず、「通話時間の上限に達しました」を返す（I09 の経路で画面に表示される）。

### 3.2 判断が分かれる点（オーナーに決めてほしい）

**Q1. 通話を切ってすぐ掛け直したとき、30分はリセットされるか**

| 案 | 内容 | 利用者から見ると | 抜け道 |
|---|---|---|---|
| **A（推奨）** | どちらかが「切る」を押したらセッションを閉じる（`ended_at` を記録）。掛け直しは新しい30分 | 今までどおり「1回30分」。切って掛け直せばまた30分話せる | 双方が改造アプリで「切る→即掛け直し」を自動で行えば延長できる。ただし**正規の掛け直しと区別できず、仕様上も許されている操作**なので、実害は「1回30分」の範囲に収まる |
| B | 最初の発行から31分間は、切っても掛け直しても同じ期限 | 5分で切って掛け直すと「残り25分」になる。画面の表示も「残り25分」から始まる | 最も堅い。ただし「つながらずに掛け直した」だけで時間が減る |
| C | B に加え、つながらなかった（無応答・拒否）場合だけリセット | B の不便を減らす | 「つながったか」をサーバーが知る手段が要る（calls 行の作成を待つ等）。実装が複雑 |

推奨 A の理由: SPEC とオーナー決定の文言は「1回30分」で、1日の総時間の制限は無い。A は取り直しによる**1回の通話の延長**（Grok#3 の指摘そのもの）を防ぎ、正規の掛け直しの体験を変えない。

**Q2. 「切る」をサーバーへ伝える方法（A の場合）**

- A-1（推奨）: `agora-token` に `{ matchId, action: 'end' }` を足す（当事者のみ。既存の資格チェックを通す）。画面の「切る」と相手切断時に呼ぶ。
- A-2: 既存の `calls` 行（発信側が接続時に作る）の `ended_at` を見る。着信側だけ残った場合や、接続前に切った場合を拾えない。

### 3.3 その他

- 画面のタイマーは、トークン応答の `expiresAt − 60秒` を「30分の終わり」として表示・切断する（掛け直しでセッションを再利用した場合も表示と実際の切断が一致する）。
- `calls` 表（通話記録）の扱いは変えない（I39 は別途）。

## 4. リスクレベル: **高**（通話・本番設定に準ずるサーバー判定、新しい表）

## 5. リスク・副作用

- DB 障害時は通話を始められない（I28 と同じ安全側）。
- 本番反映順: migration → agora-token のデプロイ → アプリ配信。旧アプリは `expiresAt` を使わないが、トークン期限はサーバーで守られるので危険はない（表示と切断がずれるだけ）。
- Agora の実キーが無いと、実際の切断タイミングは確かめられない（ローカルではトークンの有効期限の値を確認するまで）。

## 6. 動作確認方法

- SQL: `call_sessions` に利用者が触れないこと（権限テスト）。
- ローカル Edge Function（ダミーキー）: 1回目の発行で `expiresAt ≈ now+31分`、1分後の再発行で `expiresAt` が変わらない、`action:'end'` 後の発行で新しい期限になる、他人のマッチは拒否、DB 障害時は 500。
- 実音声: Agora キー設定後に 2 ブラウザで、30分で両方が切れること・取り直しても延びないこと。
