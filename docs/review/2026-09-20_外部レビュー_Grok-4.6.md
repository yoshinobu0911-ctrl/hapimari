### #1 補足（二重決済）

`stillValid` は **DB 行だけ**を見る。Webhook 取りこぼし時のフェイルセーフは「期限が切れたら送れなくなる」方向（`is_subscription_active`）で、**「支払ったのに DB が incomplete のまま → もう一度 Checkout できる」**方向は無い。

加えて Checkout セッションは 31 分有効で、同一 Customer に複数セッションを並べる禁止が無い。Web は遷移中ボタン無効のままだが、ネイティブは URL を開いた直後にボタンを戻す。別端末・別タブでも同様。

失敗時のユーザー被害は「請求が2本」で、Webhook の置き換えガード（`entitledIncoming`）は **DB 上の契約 ID を新しい方へ上書き**するだけで、Stripe 上の旧契約は生きる。

### #2 補足（いいね 1000 件）

R4 の表示上限は 1 日 100 件だが、保存は全件。`assignVisibleDates` は **取得できた配列だけ**を昇順に見る。`max_rows=1000` は「エラーを返さず切る」。累計 1000 を超えた女性は、新しいいいねが見えない。レビュー依頼の想定規模（会員1万人・いいね1000件）ちょうどで壊れる。

### #3 補足（15分）

クライアントタイマー（`remainingCallSeconds`）と `token-privilege-did-expire` は正規アプリでは効く。サーバーは「このマッチで既に発行したトークンの有効開始」を持たない。改変 Web クライアントや直接の Function 呼び出しが対象になるか、オーナー確認が必要。

## 4-4. オーナー向けサマリ

いちばん危ないのは **お金が二重に引かれる経路**（指摘1）です。決済の「正」を Stripe ではなく、手元の DB だけ見ているため、通知の遅れやボタンの連打で同じ人が二回払える穴があります。公開してカードを通す前に直すべきです。

次に、**もらったいいねが1000件を超えると新しい分が黙って消える**（指摘2）です。人気の女性会員で、公開後すぐ起き得ます。

公開前に必ず直すもの（must）は **2件**です。確認が必要なもの（ask）は **2件**（通話15分を改変アプリまで防ぐか、決済通知の取りこぼしをどう復旧するか）。残りは手順書の古さや、エラーメッセージが利用者に届かない類です。

SQL テストの「全部緑」表示は、95a4776 時点ではエラーを数えていません。緑だから安全、とは限りません。

法令の届出・本番キー未設定は今回の対象外（既知）です。

### 5-2. 反論・補強の詳細

#### 反論: 4055524034

原文（基点 d3d0711）は `PHOTO_MODERATION_API_KEY` が `apps/admin/.env.example` に無い、としている。対象コミット `95a4776` では次が存在する。

# 写真審査へのAI判定併用（...2026-09-09オーナー承認）。
PHOTO_MODERATION_API_KEY=sk-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

コミット `2a7c842`（写真AI）で解消済み。nits として残す必要はない。

#### 補強: 4055523936

先 INSERT の窓（209行→221行）に同意する。失敗時の delete（224行）は「throw したとき」しか動かない。プロセスキル・タイムアウトでは行が残る。

それだけだと「払ったのに使えない」。当方 #1 は、その状態の利用者が Checkout をもう一度踏めることまでつながる。復旧を利用者の再決済に頼ると **二重請求** になる。`processed_at` に加え、Checkout 側で `subscriptions.list({ customer, status: 'active' })` を正とすることが対になる。

#### 補強: 4055523990
