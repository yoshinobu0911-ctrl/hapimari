$ARGUMENTS

# 0. 最初にやること — モデルの使い分け判定

このコマンドは**下位モデル（Sonnet 等）で実行してよい**設計になっています。
ただし、設計そのものを下位モデルが作ってよいかは、リスクで決まります。

まず、依頼が次のどれかに触れるかを判定してください。

**センシティブ領域**: 認証／権限・RLS／個人情報／写真・書類／メッセージ／マッチング／
通報・ブロック／年齢・本人確認／決済／管理画面／不正対策／本番設定

**土台判断**: DBスキーマ／認証モデル／権限モデル／データの持ち方
（＝後から変えると作り直しになる判断）

- **どちらかに触れる → 設計は上位モデルに任せる。** 以下を出力して**いったん止まる**：

  > この依頼は〈センシティブ領域／土台判断〉に該当します。設計は上位モデルで作ります。
  > 次のコマンドを実行してください:
  > `/advisor-design $ARGUMENTS`
  > 設計書が `docs/design/` に出たら、この会話に戻って「設計に従って実装して」と伝えてください。

  自分で設計を書き始めないこと。ここを省略するのが最も高くつく失敗です。

- **どちらにも触れない → そのまま下に進み、自分で設計提案を出す。**

# 1. 設計提案に含めるもの（リスク低の場合）

1. **目的の確認** — 依頼をどう解釈したか（ズレていたらオーナーが訂正する）
2. **変更範囲** — 触るファイル・テーブル・Edge Function の一覧と規模感（S/M/L）。最小構成で
3. **設計方針** — 実装アプローチ。判断が分かれる点は「選択肢A/B＋推奨案と理由」
4. **リスクレベル**（中/低）と、既存機能・既存データへの副作用
   ここで「高」だと気づいたら、**0に戻って `/advisor-design` に回す**
5. **動作確認方法** — 非エンジニアのオーナーが自分で実行できる手順（正常系と、エラーになるべき異常系の両方）
6. **確認質問**（最大3つ）

# 2. 進行ルール

- リスク「中」: 提案を出し「このまま進めてよいか」を一度確認してから実装
- リスク「低」: 提案と実装を1回でまとめてよい（変更内容は必ず報告）
- 上位モデルの設計書がある場合は、**その設計の範囲だけを実装する。** 設計に無い判断が必要になったら、
  勝手に決めず、止まって「設計に無い判断が出た」と報告する
- 実装は承認された範囲のみ。途中で範囲を広げたくなったら、止まって相談する

# 3. 実装が終わったら

続けて `/selfreview` を必ず実行する（事実の整理と機械チェック）。
その結果を見たうえで、オーナーが `/advisor-review` を実行し、上位モデルの監査を受ける。
