# 設計提案に含めるもの

1. **目的の確認** — 依頼をどう解釈したか（ズレていたらオーナーが訂正する）
2. **変更範囲** — 触るファイル・テーブル・Edge Function の一覧と規模感（S/M/L）。最小構成で
3. **設計方針** — 実装アプローチ。判断が分かれる点は「選択肢A/B＋推奨案と理由」
4. **センシティブ領域チェック** — 認証/権限・RLS/個人情報/写真・書類/メッセージ/マッチング/
   通報・ブロック/年齢・本人確認/決済/管理画面/不正対策/本番設定 のどれに触れるか。
   触れる場合は「誰が・何を・新たに見られる/できるようになるか」を具体的に
5. **リスクレベル**（高/中/低）と、既存機能・既存データへの副作用
6. **動作確認方法** — 非エンジニアのオーナーが自分で実行できる手順（正常系と、エラーになるべき異常系の両方）
7. **確認質問**（最大3つ）

# 進行ルール

- リスク「高」（センシティブ領域）: オーナーが「OK」と返すまで絶対に実装しない
- リスク「中」: 提案を出し「このまま進めてよいか」を一度確認してから実装
- リスク「低」: 提案と実装を1回でまとめてよい（変更内容は必ず報告）
- 実装は承認された範囲のみ。途中で範囲を広げたくなったら、止まって相談する
- 実装完了後は、続けて `/selfreview` を必ず実行する
