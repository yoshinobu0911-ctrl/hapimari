## 1. エグゼクティブサマリ

**結論：現状のままリリースしてはいけません。** 「ブロック・退会・位置情報・写真・管理画面」という“脆弱ユーザーを守る仕組み”が、DB とアプリの両方で実際には機能しておらず、加害者からの連絡・自宅位置の特定・顔写真の一括収集が可能な状態です。機能そのものは概ね設計どおり動きますが、**安全要件の実効性に系統的な穴**があり、そこを塞ぐまでは公開不可という評価です。

## 2. 最優先で直すべきもの（P0 / リリース前必須）

### P0-1. ブロックしても相手からメッセージが届き続ける
- **何が起きるか**：ハラスメント相手をブロックしても、DB・アプリのどちらでもメッセージの送受信を止めていません。加害者は今までどおり送信でき、被害者の画面にリアルタイムで届き続けます。退会済み相手からの送信も同様に成功し、被害者側にはその会話を消す手段もありません。確認ダイアログの「お互いに表示されなくなる」という約束と実態が食い違っています。中高年・再婚という脆弱層向けの中核安全機能が実質破綻しています。
- **根拠**：`supabase/migrations/20260707300000_m6_subscription_location.sql:58`（messages INSERT ポリシーにブロック判定なし）、`supabase/migrations/20260705100000_init.sql:248`（messages SELECT）・`:241`（matches SELECT）も同様。`apps/mobile/src/app/modal/report-block.tsx:68`（blocks に1行 INSERT するだけで match を無効化しない）。
- **最小修正**：messages の INSERT/SELECT と matches の SELECT に「相手が非ブロック かつ status='active'」条件を追加する。または、ブロック時に該当 match を無効化する security definer な RPC を用意し、report-block から同時に呼ぶ。

### P0-2. 任意ユーザーの居場所を約1km精度で追跡できる
- **何が起きるか**：距離取得 RPC（`get_profile_distances`）に「相手を見てよいか」の認可がなく、かつ自分の座標を自由に詐称できるため、地点を3か所に変えて距離を取れば三辺測量で相手の位置を特定できます。ブロックした相手・退会/凍結した相手・一度も接点のない相手の位置まで割り出せ、退会後も座標が消えないため無期限に追跡可能。ストーキングに直結します。
- **根拠**：`supabase/migrations/20260707310000_m6_location_table.sql:62`（認可フィルタなし・security definer で RLS を貫通）、`:39`（`set_my_location` が座標を検証せずレート制限もなし）、`20260707300000_...:101`（退会処理が `profile_locations` を削除しない）。
- **最小修正**：`get_profile_distances` に `join profiles p on p.id=l.user_id and p.status='active' and not is_blocked_between(auth.uid(), l.user_id)` を追加。退会処理で `profile_locations` を削除。距離開示をマッチ/discover 結果に限定し、`set_my_location` の更新頻度を制限する。

### P0-3. 全会員の顔写真を未認証で一括ダウンロードできる
- **何が起きるか**：写真バケットが公開設定かつ閲覧ポリシーが匿名（anon）にも開いているため、Storage の一覧 API で全会員の写真を無認証で列挙・一括取得できます。保存 URL は恒久的なので、退会・凍結・ブロック後も失効せず、プロフィール側の非表示制御を貫通します。晒し・なりすまし素材化のリスク。
- **根拠**：`supabase/migrations/20260706000000_storage_photos.sql:7-8`（`public=true`）・`:11-13`（SELECT ポリシーに `to authenticated` 指定なし）、`apps/mobile/src/lib/upload-photo.ts:27`（恒久 URL を profiles に保存）。
- **最小修正**：バケットを `public=false` にし、SELECT を `to authenticated` かつ閲覧関係（active・非ブロック）に紐づけ、表示は短命の署名 URL 経由にする（管理画面 verifications の `createSignedUrl` 既存パターンを踏襲）。最低でも匿名の一覧を封じる。

### P0-4. 管理画面が無認証で、到達すれば誰でも全会員 PII と凍結/承認操作ができる
- **何が起きるか**：`apps/admin` に認証もミドルウェアもなく、全画面が RLS をバイパスする service_role で動いています。本番相当環境にデプロイすると、URL に到達した第三者が全会員 PII の閲覧、任意ユーザーの凍結、本人確認の不正承認、本人確認書類の署名 URL 発行までできます。QUESTIONS.md Q5 で既知とされながら M6 完了後も未解決です。
- **根拠**：`apps/admin/lib/supabase-admin.ts:12`（service_role＋デモキーのハードコードフォールバック）、middleware・認証ガード不在、`apps/admin/app/users/actions.ts`・`verifications/actions.ts`（無認証の server action）。
- **最小修正**：本番前に管理者認証＋ミドルウェアによる全ルート保護を必須化。service_role キーのハードコードフォールバックを削除し、未設定なら起動失敗させる。Q5 を「ブロッカー」欄に昇格。
- **補足**：現状デプロイ設備がないため“今すぐ”の被害はありませんが、「認証を足さずに1回デプロイする」だけで顕在化します。手続き上のガードが効いていない点が問題です。

### P0-5. 全会員の正確な生年月日と「非表示のはずの子ども情報」が API に載っている
- **何が起きるか**：discover などが `profiles.select('*')` しており、authenticated に全カラムが開放されているため、閲覧のたびに完全な生年月日（`birth_date`）と、プロフィールに表示しないとオーナー決定済みの子ども関連情報（`has_children` ほか）がレスポンスに載ります。開発者ツールや簡単なスクリプトで全会員分を収集可能で、製品として明示的に隠す約束をした情報が漏れています。
- **根拠**：`apps/mobile/src/lib/discover-query.ts:28`ほか `profile/[id].tsx:80`・`likes.tsx:70`・`messages.tsx:63` の `select('*')`。`20260706010000_explicit_grants.sql:20` / `20260707310000_...:36` のテーブル単位 GRANT。UI は年齢（`calcAge`）しか表示しない。
- **最小修正**：サーバ側で計算した年齢（view か生成列）を公開し、`birth_date` と子ども関連カラムの SELECT を authenticated から REVOKE。discover の年齢フィルタは view/RPC 経由に移す。各所の `select('*')` を明示カラムリストへ置換。

### P0-6. 退会したユーザーが再ログインすると“誰からも見えないゾンビ状態”で使い続ける
- **何が起きるか**：入口ゲートが status を見ないため、退会（withdrawn）後に再ログインすると通常どおり discover に入れます。閲覧はできるのに、いいね・メッセージは拒否され、しかも「本人確認をご確認ください」という誤った案内が出ます。復帰導線がなく、本人は退会状態と気づかないまま活動します（承認済み受け入れ条件 M6-4「再ログインは退会済み案内のみ」が未実装）。
- **根拠**：`apps/mobile/src/app/index.tsx:27`（status 判定なし）、`use-my-profile.ts`（status フィルタなし）、`init.sql:189-191`（本人は自分の行を取得できる）。
- **最小修正**：index.tsx で `status==='withdrawn'`（および `suspended`）を判定し、専用の案内画面へ分岐する。復帰を許すなら `reactivate_account` RPC の追加をオーナーに提案。

### P0-7. 1アカウントで無実のユーザーへの「通報3件」警告を偽造できる
- **何が起きるか**：通報テーブルに自己通報防止も重複防止もなく、管理画面の警告閾値が「通報者の人数」ではなく「open 件数の生数」で判定されます。1人が3回通報するだけで被通報者に赤枠警告が付き、管理者に手動凍結を誘発できます（brigading）。本人確認前・凍結済みアカウントからでも通報でき、通報一覧に上限がないためキューの洪水も可能です。
- **根拠**：`init.sql:99-107`（check/unique なし）・`:284-289`（RLS/GRANT）、`apps/admin/app/reports/page.tsx:66-69`（生件数集計）、`report-block.tsx`（クライアント直 INSERT）。
- **最小修正**：`reports` に `check(reporter <> reported)` と、open 中の重複を防ぐ部分ユニークインデックス（`(reporter, reported) where status='open'`）を追加。page.tsx の集計を `Set` で通報者の重複排除に変更。

### P0-8. 写真の GPS 情報（EXIF）が残り、公開 URL から自宅座標が数メートル精度で漏れる
- **何が起きるか**：写真アップロードに EXIF 除去がなく、Web 経路では位置情報付き原本がそのまま公開バケットに保存されます。P0-3 の「未認証一括取得」と組み合わせると、exiftool 等で全会員の自宅座標・撮影日時・機種を抽出できます。ネイティブで EXIF が落ちるのは再エンコードの副作用にすぎず、設定変更で即破綻します。
- **根拠**：`apps/mobile/src/lib/upload-photo.ts:14-24`（EXIF 除去なし・生バイトをそのまま保存）、expo-image-picker の Web 実装が生バイトを返す、`storage_photos.sql:7-8`（公開バケット）。
- **最小修正**：`uploadProfilePhoto` の冒頭で全プラットフォーム共通に `expo-image-manipulator`（resize＋compress＋JPEG 再エンコード）を通してからアップロード。恒久策は Edge Function 経由でサーバ側再エンコード・メタデータ除去。

### P0-9. iPhone 標準設定で撮った本人確認書類（HEIC）が管理画面で表示できず審査が詰まる
- **何が起きるか**：HEIC 書類が再エンコードされず生バイトで保存され、管理画面が `<img>` で表示するため Chrome/Edge/Firefox では表示できません。審査担当が承認/却下を判断できず、iPhone 既定設定（高効率/HEIF）で撮る主要ユーザー層の必須本人確認（＝メッセージ送信の解錠条件）が広範に止まります。
- **根拠**：`apps/mobile/src/lib/upload-verification.ts:18`（HEIC を拡張子 jpg・contentType image/heic で格納）、`apps/admin/app/verifications/page.tsx:77`（`<img>` 描画）。
- **最小修正**：提出前に `expo-image-manipulator` で JPEG 再エンコード（P0-8 も同時解決）。最低でも jpeg/png/webp 以外は再エンコードを必須化し、拡張子と contentType を実バイトの形式に一致させる。

## 5. 棄却された指摘の要約（再監査の無駄を防ぐため）

1. **いいねの carriedOver フラグが R4 定義と二重化** → フラグはクライアント未使用で、表示は正典の `assignVisibleDates` が決定。設計書どおりで実害なし。
2. **退会後も `subscription_active` が true のまま残る** → 退会中は messages RLS も active を要求し無効、課金は常時成功モックで金銭価値ゼロ、承認済みソフトデリート設計。
3. **`subscription_active` 列が全員に見える** → 直前 migration のカラム GRANT で既に付与済み（当該行の巻き添えではない）、M6 で SELECT 可と承認済み、R9 仕様上「送信可＝課金済み」は元々公知。
4. **透明性レポート2指標が近似値** → QUESTIONS.md Q17＋引き継ぎ資料に記録済みの意図的暫定仕様、未公開で admin 表示のみ。
5. **seed 末尾の UPDATE が UUID 非限定** → 実行経路は空 DB 再構築の `db reset` のみで挙動は同一、本番環境が存在せず、SPEC 上「デモ男性=課金」は仕様。
6. **全 FK に on delete 指定がなくハード削除不能** → 承認済みソフトデリート設計の帰結。cascade 付与はむしろ通報証跡を危険に消す。
7. **`review_verification` が reviewed_by を設定しない** → 管理画面に審査者アイデンティティ自体が未実装（Q5）で記録すべき値がなく、M2 はモック、fix 案も型不整合。
8. **CI が型チェックしない** → SPEC の M0 が「CI（lint+test）」と規定。型チェックは各マイルストーン受け入れで `tsc --noEmit` として実施済み。
9. **flagged 一覧が50件 limit のみ** → M3 設計 §6.3 どおりの意図実装、対応は /reports に集約、R8 受け入れ条件は充足（将来拡張提案）。
10. **本人確認書類の EXIF 漏洩（別経路）** → verifications バケットの MIME allowlist が HEIC/TIFF/AVIF を 415 で拒否し原本保存が成立せず、WebP 経路は iPhone が生成しないため非現実的。

## 6. 総評

**MVP の品質評価**：機能実装は概ね設計どおりで、各マイルストーンの受け入れ条件も多くが満たされています。個々のロジックは丁寧で、正規化・モック境界・設計判断の記録（decisions/QUESTIONS）も整っています。**弱点はコードの巧拙ではなく「安全機能の実効性を横断的に検証する仕組み」の欠落**に集中しています。ブロック・退会・位置情報・写真・管理画面という“脆弱ユーザー保護の背骨”が、DB とクライアントの両層で担保されておらず、これが本 MVP のリリース最大の障害です（P0 の9件中7件がこのテーマ）。

**次マイルストーンで投資すべき技術ポイント（3つ）**

1. **関係性ベース認可の一元化**：profiles の SELECT ポリシー（active＋非ブロック）を唯一の基準として `is_blocked_between` を単一の認可関数化し、messages・matches・photos・位置情報 RPC の全経路から参照する。これで P0-1/2/3/5 の根っこ（各機能が個別にブロック判定を持たない/持たせ忘れる）が一括で塞がる。
2. **退会/凍結の状態機械の集約**：`withdraw_account` を「status 更新＋関連データ（位置・写真・課金フラグ）の後始末＋入口ゲートの分岐＋管理操作の status ガード」まで含む1本の検証済みフローにまとめ、状態遷移を1箇所に集める。P0-6・P1-10 と棄却済みの退会系論点をまとめて安定化できる。
3. **画像処理パイプラインの標準化＋管理画面の認証ゲート化**：写真・本人確認の全アップロードを Edge Function 経由でサーバ側 JPEG 再エンコード＋EXIF 除去に統一し、P0-8（EXIF 漏洩）・P0-9（HEIC 審査不能）・formatばらつきを一挙に解消。あわせて P0-4 の管理画面認証を「本番デプロイの必須ゲート」として仕組みに組み込む。
