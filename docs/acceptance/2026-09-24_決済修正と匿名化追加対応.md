## 4. レビュー観点（委託エンジニア向け）

- **`stripe-webhook/index.ts` の `confirmSubscriptionSwitch`**: 別契約IDへの切り替えを確認できない場合、Webhook処理の中から**Stripeの新しい契約を自動でcancelする**設計にした（二重契約の疑いを止める§3.3層3の実装）。Webhook処理中に決済側へ書き込みを行う数少ない箇所であり、公開前に必ず確認してほしい。
- **冪等キーの設計**: Customer作成は利用者単位で固定（`hapimari-customer-${user.id}`）、Checkout Session作成は予約単位で固定（`hapimari-checkout-${claimToken}`）。Stripe API呼び出し後に応答を失い、かつ2分の予約タイムアウトを超えてから再試行された場合、新しいclaimTokenで再作成されるため理論上はSession/Customerが増える余地が残る（設計提案自身が認めている残存リスクと同水準。専用の処理基盤を作らない方針のため許容）。
- **`stripe-cancel` の `reconcileTermination`**: `resource_missing`（契約IDがStripeに無い）を「終了」とみなす前に、同じCustomerが引けることを確認する設計にした。テスト/本番キーの取り違えを終了と誤判定しないためだが、この分岐は自動テストでは再現できていない（Stripe側のエラー形状に依存するため、実キーでの確認を推奨）。
