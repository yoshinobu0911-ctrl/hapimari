## 2. 絶対に守るルール

1. **読み取り専用。** ソース・設定・migration・ドキュメントを一切変更しない。`git add` / `git commit` / `git push` / `git stash` も禁止。
2. **アンカリング禁止（順序厳守）。** §4 の成果物を書き終えるまで、次のファイルを**開かない**:
   - `docs/review/2026-09-20_AIレビュー原文.md`
   - `docs/review/2026-09-20_修正指示書.md`
   - `docs/review/2026-09-20_引き継ぎプロンプト.md`
   - `docs/review/2026-09-20_外部レビュー_*.md`（他モデルの成果物）
3. **根拠のない指摘を書かない。** すべての指摘に「ファイル:行番号」と、実際のコード引用または実行結果を添える。推測で「〜かもしれない」だけの指摘は「低確度」欄に分けて書く。
4. **既知の見送りを蒸し返さない。** `docs/review/2026-09-02_指摘棚卸し.md` に「意図的見送り」「本番実測待ち」と記録済みの項目は、**その判断が誤りだと示せる新しい根拠がある場合のみ**再提起する。
5. **「実キー未設定で動作未検証」は既知。** Stripe / Agora / OpenAI の実キーは未設定で本番未デプロイ。これ自体をバグとして報告しない（ただし「キーが入っても動かない」ロジック上の欠陥は報告対象）。
6. **テストを信用しすぎない。** `scripts/run_sql_tests.sh` の「全PASS」表示は、アサーションの作りによっては空振りしうる。緑の表示ではなく、アサーションが本当に何を検証しているかを読んで判断する。
7. `supabase start` や `pnpm test` など**副作用のないコマンドの実行は可**。ローカルDBへの書き込みは、テストスクリプトの実行以外では行わない。

## 4. 成果物（必ずこの形式で）

ファイル `docs/review/2026-09-20_外部レビュー_codex.md` を新規作成する（同名ファイルが既にあれば `_codex-2.md` のように連番を付け、既存ファイルは変更しない）。冒頭に、自分が動作しているツール名とモデル名を1行書く。構成は次のとおり。

### 4-1. カバレッジ
読んだファイル一覧、実行したコマンドと結果、**見なかった領域**を明記。

### 4-2. 指摘一覧（表）
| # | 種別 | 領域 | ファイル:行 | 指摘（1文） | 失敗シナリオ（具体的な入力→誤った結果） | 根拠（コード引用 or 実行結果） | 修正案 | 確度 |
|---|---|---|---|---|---|---|---|---|

- **種別**は既存レビューと揃える: `must`（放置すると障害・漏えい・法令違反）/ `ask`（意図確認）/ `suggestion`（改善提案）/ `imo`（意見）/ `nits`（軽微）
- **確度**: 高（コードで確認済み）/ 中（コードは読んだが実行未確認）/ 低（推測）
- 1件1行。長い説明は表の下に「#番号」見出しで補足する
- `must` を優先し、表は `must` → `ask` → `suggestion` → `imo` → `nits` の順に並べる

### 4-3. 見送った候補
指摘にしなかったが気になった点と、しなかった理由（既知の見送りと重複／根拠不足／設計上の意図と判断 など）。

### 4-4. オーナー向けサマリ（非エンジニア向け・10行以内）
何が一番危ないか、公開前に必ず直すべきものは何件か、を平易な日本語で。

## 5. 突き合わせ（§4 を書き終えてから）

ここで初めて `docs/review/2026-09-20_AIレビュー原文.md`（既存22件）を読み、自分の成果物の末尾に次の節を追加する。

### 5-1. 既存22件との対応表

|---|---|---|---|

- 判定は次の4択: **同意**（自分も見つけた／読んで妥当）/ **反論**（誤りまたは過大。根拠を書く）/ **未確認**（自分の範囲外）/ **補強**（同意したうえで追加情報あり）

### 5-2. 反論・補強の詳細
