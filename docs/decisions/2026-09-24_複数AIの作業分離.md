# 2026-09-24: 複数AIの作業を「フォルダ・ブランチ・担当」で分ける

状態: **提案（オーナー承認待ち）**。導入手順: `docs/handoff/2026-09-24_multi-agent-setup.md`

## 背景（点検で分かった事実）

オーナーから依頼があった: 各AI（Claude Code / Codex / Grok）の作業がぶつからない（バッティングしない）フォルダ構成になっているか点検してほしい。
点検の対象は GitHub 上のリポジトリ（main の全105コミット）。ローカルの未コミット変更と `C:\Users\haosh\dev\AGENTS.md` はクラウドから見えないため、まだ確認していない（導入手順の中でローカルの Claude Code が確認する）。

| # | 事実 | 根拠 |
|---|---|---|
| 1 | 全AIが同じフォルダ・同じブランチ（main）で作業している | CLAUDE.md §3「作業は必ず `C:\Users\haosh\dev\hapimari`」。GitHub のブランチは main と review-base（レビュー用の空基点）のみ。105コミットすべてが main に直接積まれ、マージは0件 |
| 2 | 未コミットの作業が溜まり、あとから仕分けてコミットした前例がある | HANDOFF.md §1「未コミットだった全作業…を論理単位6コミットに整理」（2026-08-19 16:20〜16:22 の6コミット）。08-26 には並行セッションも発生 |
| 3 | 開発憲法（CLAUDE.md）は Codex・Antigravity には自動で読まれない | Codex は AGENTS.md（と設定した代替名）しか読まない。リポジトリ直下に AGENTS.md が無く、`apps/*/AGENTS.md` は Expo・Next.js の雛形（バージョン注意書き）だけ |
| 4 | 共通ルール `dev\AGENTS.md` がリポジトリの外にある | tasks.md・progress.md が参照している。Git 管理外なので履歴が残らず、委託エンジニアやクラウドのセッションから見えない。Codex を hapimari フォルダで起動した場合、Git のルートより上にある AGENTS.md は読まれない |

| 6 | 全員が同じ場所に書くファイルが衝突の中心になっている | 変更回数の上位: progress.md 17回・database.ts（DBから自動生成）15回・QUESTIONS.md 11回（番号が連番なので取り合いになる）・pnpm-lock.yaml 8回 |

良い点（今後も維持する）:
- 決定記録・レビュー記録は日付付き、migration は時刻付きのファイル名なので、ファイル名同士は衝突しにくい
- apps/mobile・apps/admin・packages/shared・supabase の役割分けが明確
- progress.md（作業ログ）・tasks.md（未完了）・QUESTIONS.md（止まる質問）の役割分担が決まっている

## 決めたいこと（提案）

1. **1つのAIセッション = 1つの作業フォルダ（git worktree）= 作業ごとに1つのブランチ**。本体フォルダは統合とオーナーの確認専用にする
2. **main への取り込みは、Claude Code がレビューしてから行う**（merge commit に「どのAIの作業か」が残る）
3. **`supabase/`（DB・Edge Function）と、DBから生成するファイルは、同時に1つのAIだけが触る**。原則 Claude Code が担当する
4. **共通ルールはリポジトリ直下の `AGENTS.md` に置く**。全AIが読む入口にし、CLAUDE.md からも自動で読み込む
5. コミットの最後の行に `Agent: <AI名>` を付ける。QUESTIONS.md の新しい番号は `Q-YYYYMMDD-<AI名>` の形にする

詳細なルールは `AGENTS.md` に書く。

## 選択肢

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A. 時間で分ける | 今の1フォルダのまま、同時に動かすAIを1つに限る。交代時は必ずコミットする | 追加の準備が要らない | 並行作業ができない。コミット忘れで作業が混ざる問題（事実2）は残る |
| **B. 作業フォルダを分ける（推奨）** | AIごとに git worktree（別フォルダ）とブランチを使う | 同時に動かしてもファイルとコミットが混ざらない。履歴は1つなので統合がローカルで簡単に済む | フォルダごとに `pnpm install` と `.env` のコピーが必要。DBとポートは共有のまま（ルールで補う） |
| C. 丸ごと別コピー | AIごとにリポジトリを別に clone する | B と同じくらい分離できる。仕組みが単純 | 統合のたびに GitHub 経由の push/fetch が必要。容量も増える |
| D. GitHub の PR で統合 | 各AIがブランチを push し、PR でレビューしてから取り込む | CI とレビュー記録が GitHub に残る | オーナーの操作が増える。B と組み合わせて後から導入できる |

## B を推す理由

- 事実1・2（同じフォルダで作業するので混ざる）を根本から防げるのは B か C。B は履歴を共有しているので、統合がローカルで完結して簡単
- 本体フォルダは、オーナーの起動用 bat が指す場所のまま残せる（オーナーの操作の変化が小さい）
- A では「コミット忘れ」を防げない（事実2の前例がある）

## 残るリスク

- ローカルDBとポートは、フォルダを分けても共有のまま → `AGENTS.md` §3・§4 のルール（DB担当は1つだけ・ポート割り当て表）で運用する
- ルールを守るかどうかはAI次第 → 統合時に Claude Code がレビューして確認する（`AGENTS.md` §7）

## 元に戻す方法

`git worktree remove <フォルダ>` で作業フォルダを消し、この提案のコミットを `git revert` すれば、元の運用（1フォルダ）に戻る。
