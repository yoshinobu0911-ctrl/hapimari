# I33 メッセージ送信失敗を原因別に案内する 設計提案（2026-09-26）

> 状態: **夜間指示書 §1 により推奨案で自己承認して実装**（翌朝オーナーがコミット単位でレビュー）。
> 作成: Claude Opus 5.5（夜間自律作業・モードA）。方針: [2026-09-24 オーナー決定](../decisions/2026-09-24_レビュー残件20件の方針決定.md) I33＝A「送信失敗を原因別の案内に変更。課金期限の再確認を含む」。根拠: 統合表 I33（Grok#6）。
> 人間レビューの段階: (B) MVP 完成時。

## 1. 目的

チャット画面（`apps/mobile/src/app/chat/[matchId].tsx` の `send()`）は、送信に失敗すると原因に関係なく「送信できませんでした。本人確認の状態をご確認のうえ、時間をおいてお試しください。」と出す。課金の期限切れ・ブロック・通信断・文字数超過でも本人確認を案内してしまい、利用者は何をすればよいか分からない。

## 2. 変更範囲（規模 S）

| ファイル | 内容 |
|---|---|
| `packages/shared/src/message_send_error.ts`（新規） | 失敗の分類 `classifyMessageSendError()` と案内文 `messageSendFailureText()`（純粋関数） |
| `packages/shared/src/index.ts` | export を1行追加 |
| `packages/shared/test/message_send_error.test.ts`（新規） | 分類と文言のテスト |
| `apps/mobile/src/app/chat/[matchId].tsx` | `send()` の失敗時に分類し、送信資格の不足なら本人の状態と課金期限をサーバーに問い合わせ直してから案内する |

DB・RLS・トリガ・Edge Function は変更しない（読み取りの RPC `is_subscription_active` は既存・利用者が実行可）。

## 3. 設計方針

### 3.1 実測した失敗の種類（ローカル REST で確認）

| 原因 | サーバーの応答 | 分類 |
|---|---|---|
| 送信資格なし（男性の未課金・期限切れ／本人確認前／非在籍） | 400 `P0001` `not_entitled`（トリガ `_enforce_message_entitlement`） | `not_entitled` |
| ブロック・当事者でない | 403 `42501` RLS 違反 | `rejected` |
| 本文が2000字超 | 400 `23514`（`messages_body_check`） | `too_long` |
| 通信断 | supabase-js が `code: ''`・`TypeError: Failed to fetch` 等 | `network` |
| その他 | — | `unknown` |

### 3.2 案内文（画面にそのまま出す日本語）

| 分類 | 状態の再確認 | 案内 |
|---|---|---|
| not_entitled | 自分が在籍中でない | ただいまメッセージを送信できません。アカウントの状態をご確認ください。 |
| 〃 | 本人確認前 | 本人確認の完了後に送信できます。お手続きの完了をお待ちください。 |
| 〃 | 男性で課金が有効でない（`is_subscription_active` を問い合わせ直す） | 有料プランの有効期限が切れているため送信できません。プランの画面からご確認ください。 |
| 〃 | どれにも当たらない | 送信できませんでした。時間をおいてお試しください。 |
| rejected | — | このお相手には現在メッセージを送れません。 |
| too_long | — | メッセージは2000文字以内で入力してください。 |
| network | — | 通信できませんでした。電波の良い場所で、もう一度お試しください。 |
| unknown | — | 送信できませんでした。時間をおいてお試しください。 |

「課金期限の再確認」: `profiles.subscription_active` は定期処理で補正される列なので、期限が切れた直後は true のまま残りうる。送信資格なしで失敗したときは、`is_subscription_active(自分)` を問い合わせ直し、あわせて自分のプロフィールのキャッシュを取り直す（画面の「プランに登録」表示も最新になる）。

### 3.3 判断が分かれる点（推奨で進める）

| # | 論点 | A（推奨・採用） | B | 理由 |
|---|---|---|---|---|
| 1 | 文言の置き場所 | shared の純粋関数（Vitest でテスト） | 画面内に直書き | apps/mobile にテスト実行器が無い。分類ロジックを自動テストできる |
| 2 | ブロックと「相手が退会」を区別するか | 区別しない（「このお相手には現在メッセージを送れません」） | 区別する | 区別すると「相手にブロックされた」ことが推測できてしまう（相手のプライバシー）。いいねの blocked 文言とも揃う |
| 3 | 送信前に資格を確かめるか | しない（失敗したときだけ問い合わせ直す） | 毎回事前に確かめる | 通信回数を増やさない。サーバー側（RLS・トリガ）が最終判定であることは変わらない |

## 4. リスクレベル: **中**（メッセージ機能の画面表示のみ。サーバーの判定は不変）

憲法 §6 のメッセージ機能に触れるため規則上は「高」扱いで記録する。技術的には表示文言の分岐のみ。

## 5. リスク・副作用

- 送信の可否は変わらない（判定はすべてサーバー側のまま）。
- 失敗時だけ問い合わせが最大2回増える（プロフィールの取り直しと課金状態）。
- 通信断の判定は supabase-js のエラーの形に依存する。判定できないものは「unknown」の汎用文言になる（悪化はしない）。

## 6. 動作確認方法

- Vitest: 5分類と文言（not_entitled は状態4通り）。
- 実測の応答形（上表）を固定値としてテストに入れる。
- オーナー: 男性の未課金アカウントでメッセージを送ると「有料プランの有効期限が切れているため…」が出ること（従来は本人確認の案内だった）。
