### 4-2. 二重決済の修正方針（オーナー決定 must）

現状: `stripe-checkout/index.ts:104-117` の `stillValid` は **DB の行だけ** を見る。Checkout セッションは31分有効で、同一 Customer に複数セッションを並べる禁止が無い。ネイティブは URL を開いた直後にボタンが復活する（`subscription.tsx:153-154`）。

サーバー側（`stripe-checkout`）で3層にする。画面側の対策は補助にすぎない。

| 層 | 何をするか | 効果 |
|---|---|---|
| 1. Stripe を正にする | Checkout 作成前に `stripe.subscriptions.list({ customer, status: 'all' })` を引き、active / trialing / past_due / incomplete / unpaid が1本でもあれば DB に同期して `409 already_subscribed`（past_due は現行の §9-1 置き換え経路へ） | 「払ったのに webhook 未着で DB が incomplete」→ 再 Checkout → 二重契約、を根から塞ぐ（Grok #1 / #4 の核心） |
| 2. 開いている Checkout を1枚に保つ | `subscriptions` に `pending_checkout_session_id` を持ち、Checkout 要求時に `stripe.checkout.sessions.retrieve` で状態を見る。`open` なら **同じ URL を返す**（新規作成しない）。`complete` なら同期して 409。`expired` なら新規作成して ID を上書き | 2タブ・2端末で開いても Stripe 上の決済ページは1枚。片方で払えばもう片方は「支払い済み」になる |
| 3. それでも2本できたら止める | webhook `checkout.session.completed` で同一 Customer の有効契約が2本以上なら、**新しい方を即 `subscriptions.cancel`** し、`stripe_events` か `subscriptions` に `needs_review` 相当の印を残す。返金は Stripe ダッシュボードで手動（自動返金は実装しない＝送金操作をコードに入れない） | 最悪ケースでも「請求が2本続く」状態を作らない |

設計提案では、層2の「同じ URL を返す」と「古いセッションを `sessions.expire` してから作り直す」の A/B を示し、**推奨は前者**（作り直しは Stripe 呼び出しが1回増え、失効直後の支払い完了と競合する）。
