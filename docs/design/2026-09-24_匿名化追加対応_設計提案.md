## 1. 目的

退会から90日後に実行される `anonymize_profile()`（`supabase/migrations/20260730120000_retention_and_anonymization.sql`）が、設計方針（同ファイル7行目「個人を特定できる情報をすべて削除し、特徴量だけを残す」）どおりに全項目を処理できていない3点を直す。

- **I27**: 本人が書いた自由文が `messages.body` 以外にも残る（いいねの一言・デートの自由文・行動ログ）
- **I41**: `subscriptions.stripe_customer_id` がユーザーIDに紐づいたまま残り、Stripe Customer（氏名・メール・カード末尾を保持）経由で匿名化後も本人に戻れる
- **I42**: `reports.reason`/`detail` を対象外にしている理由・保存期間が文書化されていない

## 2. 変更範囲（規模M）

| 対象 | 変更 |
|---|---|
| 新規migration1本 | `anonymize_profile()` を `create or replace` し、下記2.1〜2.3の処理を追加 |
| `docs/legal/privacy_policy.md`（保存期間の節） | I42の保存方針を明文化（コード変更ではなく文書） |
| `scripts/test_m67_retention.sql`（既存の匿名化試験） | 追加した削除項目のアサーションを追加 |

DBスキーマ変更（列追加・削除）はない。既存関数の中身の変更と、新規テーブル変更なし。

### 2.1 自由文の追加削除（I27）

`anonymize_profile(p_user)` に以下を追加する（satoman0703さんの2026-09-21レビューで提示されたSQLを基本方針として採用。`likes`/`date_proposals` は当時の指摘どおりの形、`user_events` も同様）。

```sql
-- いいねの一言（messages.body と同じ扱い。本人が送った分のみ）
update likes set message = null where from_user = p_user;

-- デートの自由文候補のうち、本人が提案した分だけを取り除く
update date_proposals d set
  proposed_slots = (
    select coalesce(jsonb_agg(s), '[]'::jsonb)
    from jsonb_array_elements(coalesce(d.proposed_slots, '[]'::jsonb)) s
    where s ->> 'proposed_by' <> p_user::text
  )
from matches m
where m.id = d.match_id and (m.user_a = p_user or m.user_b = p_user);

-- 行動ログは行を残したまま紐付けだけ外す（集計件数は壊れない）
update user_events set actor_id = null, target_user_id = null, props = '{}'::jsonb
where actor_id = p_user or target_user_id = p_user;
```

**技術確認（satoman0703さんの記述を実コードで裏取り）**: `proposed_slots` の各要素に `proposed_by` が入っていることは `propose_date_slot()`（`20260902100000_review2_security_fixes.sql:307`）で確認した。`confirmed_slot` も `pending`（＝ `proposed_slots` の最後の要素）をそのままコピーする値（`20260819110000_m7_2b_message_kind.sql:114`）のため、**実は `confirmed_slot` にも `proposed_by` が入っている**（satoman0703さんの「誰が書いたか記録がない」はこの列には厳密には当てはまらない。ただし後述2.2の懸念は別途有効）。`area_suggestion` は単一のtext列で提案者の記録が無いことは確認どおり。

### 2.2 共有列（`confirmed_slot` / `area_suggestion`）— 判断が必要

`proposed_slots` と異なり、`confirmed_slot`・`area_suggestion` は **1組のマッチにつき1つだけ**存在し、退会していない側の相手も見ている（デート確定画面・待ち合わせ場所）。片方の退会で書き換えると、相手の画面から確定済みの日程・場所が消える副作用がある。

| 選択肢 | 内容 | 推奨 |
|---|---|---|
| A（推奨） | `area_suggestion` のみ匿名化時にNULL化（頻度が低く「らしさ」の残る自由文）。`confirmed_slot` は既に成立した事実の記録として残す（相手の体験を壊さない） | 個人を強く特定する情報ではなく地名程度、かつ相手への影響を避けられる |
| B | 両方ともNULL化（方針7行目に厳密に従う） | 相手側の画面からデート確定情報が消える。デート後であれば実害は小さいが、確定後・実施前に片方が退会した場合は相手が困る |

### 2.3 決済識別子の削除（I41）

```sql
delete from subscriptions where user_id = p_user;
```

**前提条件（重要）**: この削除は、退会時点でStripe契約が実際に終了していることが前提。[決済修正の最終差分](2026-09-24_決済修正設計提案.md) §9.5（Q2=A・退会ガード）の実装後は、`withdraw_account()` が稼働中の契約を持つ会員の退会を拒否するため、90日後にこの行を消しても「未精算の契約が宙に浮く」ことは起きない。**決済修正（§9）より先にこの削除だけを実装すると、稼働中の契約ごと消してしまう恐れがあるため、実装順序は決済修正を先にすること。**

「課金していた退会者かどうか」を学習用に残したい場合は、削除の直前に `profiles` へ真偽値1列を足す代替案があるが、今回はスキーマ変更を伴うため、必要になった時点で別途提案する（今回は削除のみ）。

## 3. リスクレベル

**高**（個人情報の削除・退会処理・決済データに関わる。AGENTS.md §6 センシティブ領域）

## 4. リスク・副作用

- **削除は不可逆**。migration適用後、対象行に対して二度と復元できない。
- 2.2でBを選んだ場合、退会していない側のユーザー体験に影響する（確定済みデートの情報が消える）。
- `scripts/test_m67_retention.sql` の既存アサーション（24項目PASS）に、今回追加した3項目分のアサーションを足す必要がある。既存分は壊さない設計だが、追加後に再実行して確認する。
- **既存の匿名化済み行への遡及適用はこの提案に含まない**（5章参照）。

## 5. 動作確認方法（実施は承認後）

1. ローカルSupabaseでseedユーザー1名を退会→`withdrawn_at` を90日前に手動でずらす→`run_retention_job()` を実行。
2. 匿名化後、`likes.message` / `proposed_slots`（本人提案分）/ `user_events.actor_id・target_user_id・props` が消えていることをSQLで確認。
3. `subscriptions` 行が消えていること、かつ決済修正§9実装後は「稼働契約がある状態では退会自体が拒否される」ことをあわせて確認（退会できた時点で契約は無い前提が成立していることの確認）。
4. 相手側アカウントから見た `confirmed_slot`・`area_suggestion` の表示が2.2の選択どおりになることを画面で確認。
5. `scripts/test_m67_retention.sql` を実行し、既存24項目PASS＋追加項目PASSを確認。

## 6. 確認質問（最大3つ）

1. **2.2の選択**: `confirmed_slot`（成立済みデートの日程・場所）を匿名化時に残すか（推奨A）、両方消すか（B）。
2. **既存の匿名化済み行への遡及補修**: 90日を過ぎて既にこの関数が実行された行が本番に存在する場合、今回の追加分（likes/date_proposals/user_events/subscriptions）を後から適用してよいか。**現時点でその該当行が実在するかは未確認**（本番DB未作成・ローカルにも実会員データはないため、いま判断できる材料がない）。本番運用開始後、該当があれば別途確認する、という整理でよいか。
3. **`reports.reason`/`detail`（I42）**: 通報原文を匿名化後も無期限で残す現状の運用を、①「安全対応のための意図的な保持」として `docs/legal/privacy_policy.md` に明文化するだけで良いか、②保存期間（例: 最終アクション後n年）を設けるか。コード変更を伴わない文書整備で良いかも含めて判断してほしい。
