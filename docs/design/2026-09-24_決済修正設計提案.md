### 2.1 なぜ指定された3列だけでは不足するか

→ §8 で決定済み（追加は4列のみ。本節の列案のうち不採用分は §8 を参照）。

`pending_checkout_session_id`はStripeから応答した後にしか保存できない。最初の2要求がともにNULLを読めば2セッションを作れてしまう。また、現stripe_eventsには契約IDがなく、event.createdだけを足しても「同じ契約の最新イベント」をDBで判定できない。指示書が求めるneeds_reviewも保存先の追加が必要。R01は現在の退会RPCを守らなければ画面を迂回できる。これらを理由として**上限超過を明示して提案で止まる**。

| 保存先 | 列・責務（案） | 既存データの扱い |
|---|---|---|
| stripe_events | `processed_at timestamptz NULL`（指定） | 一律にnowを入れない。既存IDは完了証拠がないためNULL |
| stripe_events | `event_created bigint NULL`（指定、StripeのUTC秒） | received_atから推定しない。再送または照合で実値を取得 |
| subscriptions | `pending_checkout_session_id text NULL`（指定） | 既存はNULL。NULLだけでセッションなしと判断せずStripe側を確認 |
| stripe_events | `stripe_subscription_id text NULL`（追加） | 既存はNULL。通知から特定後に保存。時刻・契約IDの索引も同migration |
| stripe_events | `needs_review boolean NOT NULL DEFAULT false`（追加） | 新しい異常の印。処理済みとは独立し、重複停止成功後も返金確認まで残す |
| subscriptions | `checkout_request jsonb NULL`（追加） | サーバー生成の作成キー・固定パラメータ・有効期限だけを保存。新規テーブルの代わりに1件だけ予約を保持 |
| subscriptions | `billing_revision bigint NOT NULL DEFAULT 0`（追加） | 古いHTTP結果が後着してDBを上書きしないための更新番号。対象行の全更新でDB側が増分 |
| subscriptions | `stripe_terminal_confirmed_at timestamptz NULL`（A案の追加） | Stripeで契約終了と未決済Sessionの不存在を確認した証拠。既存canceled行もNULLから始め、期限掃除では設定しない |

新しい列を利用者にGRANTしない。stripe_eventsは既存どおりservice_role限定。予約/確定用DB関数もPUBLIC・anon・authenticatedからEXECUTEを剥奪しservice_roleにだけ明示GRANTする。退会RPCの本人向け入口のみ現行の本人限定権限を維持する。キー、決済URL、Stripeの生イベント、カード情報、自由文はログへ出さない。checkout_requestには再送に必要な設定値/識別子だけを許可し、任意のJSONやHTTPヘッダを保存しない。

### 2.2 既存行の移行

- migration内からStripeを呼ばず、既存イベントの完了状態を推定しない。未処理NULLは安全側の初期値。
- 本番移行前に対象件数を確認し、Stripeの保持範囲内のイベントはIDから再取得して同じ署名済み再送/検証済みサーバー経路で照合する。取得できない履歴はneeds_reviewへ。古いイベントが取得できないだけで有料権限を作らない。
- 未登録の既存open CheckoutはCustomer単位で列挙・全ページ照合して採用する。複数なら新規作成を止め、不要分を失効できたことを確認する。completeの支払結果が不明なら再Checkoutを拒否する。
- サービス稼働前の運用チェックでNULL未解決・needs_reviewを確認する。workerは導入せず、再送期間を過ぎたものはStripeダッシュボードで原因確認と再送・手動照合。自動で無期限回復する仕組みではない。

## 3. 設計方針

### 3.1 通知取りこぼしと照合失敗（I06）

1. 生本文の署名を検証してからevent.id/type/event.createdを記録。署名不正は400。記録失敗は500。
2. 主キー重複時は既存行のprocessed_atを読む。非NULLなら200、NULLなら再処理する。行があるだけでは完了としない。
3. metadataとDBのCustomer・利用者の対応を確認する。照合DBエラー、対応なし、矛盾、対象更新0件は例外にして500。恒久的不一致にはneeds_reviewも立てる。metadataだけで行を新規作成して有料化しない。
4. Stripe HTTP通信はDBトランザクション外で実施。DB反映時だけ短い確定RPCを呼び、契約行とイベント行を一貫した順序でロックし、期待するbilling_revision・契約対応・processed_atを再検査する。
5. **対象1行の契約更新とprocessed_at設定を同一DBトランザクションで確定**する。競合ならロールバックしStripeから再取得、再試行上限に達したら500。古い実行結果をそのまま再利用しない。単純な「processed_atがNULLなら2実行とも更新可」にはしない。
6. 失敗時にイベント行は消さずprocessed_at=NULLのまま500。対象外typeや正当に捨てた古い通知は「適用不要として処理完了」としてprocessed_atを立てる。needs_reviewとの違いを運用手順に記載。

同じイベントの同時配送は片方の確定後にもう片方がprocessed_atを見て更新を省く。外部API操作そのものをDBトランザクションに含めることはできないため、作成は固定キー、停止は現在状態の再確認で再実行を安全にする。[Stripeの通知再送・重複・順序の説明](https://docs.stripe.com/webhooks)

### 3.2 イベント順序と別契約（I07）

- **同一sub.idの順序ガードは現行にない**。受信event.createdを保存し、その契約に反映済みのイベントの最大event.createdより古ければ、課金状態を更新せず完了にする。全Customerで一つの時刻を比較しない。
- 時刻比較と状態更新を§3.1の同じ確定RPC内で行う。同時要求が両方「新しい」と判定して後勝ちになる実装は禁止。
- event.createdは秒精度なので同秒を時系列の全順序として扱わない。同秒・状態不整合ではStripe Subscriptionの現在値を再取得し、billing_revisionが変わっていれば取得からやり直す。IDの辞書順を発生順の代わりにしない。
- 別IDの無効化イベントを捨てる既存残響ガードは維持する。ただし現行は別IDのactiveなら無条件で採用するため、**これだけではR03全体は解決しない**。正規のpending Checkoutとの対応・旧契約終了・Customerの現在契約を照合できた場合に限り新IDへ切り替える追加をQ1に含める。旧active通知だけでは再昇格させない。
- checkout/cancelによる同期も同じ確定処理へ通す。既存日次期限掃除はcurrent_period_endから利用可否を失効できるが、それだけでStripe契約がcanceledになった証拠にはしない。expire_stale_subscriptionsのDB上canceled化を見直すこともQ1の対象。

### 3.3 二重契約を防ぐ3層（I23・I24・I26）

**層1: Checkout前にStripeを照合する。** `stripe.subscriptions.list({ customer, status: 'all' })`を全ページ取得する。active/trialing/past_due/incomplete/unpaidがあれば同期して、まず新規作成を止める。active/trialingは409 already_subscribed。incompleteは進行中決済として再作成しない。past_due/unpaid等の置き換えは既存M7.2 §9-1の承認済み経路に限定し、旧契約の停止がStripeで確認できた後にだけ進む。pausedも既存の置き換え対象として照合する。照会失敗・404・権限不足を「契約なし」に読み替えない。

旧契約cancelのタイムアウト後はretrieveして結果を確認する。canceledなど終了済みを確認できなければ500または再試行案内で止め、新Checkoutを作らない。成功レスポンスを失った場合も同じ契約IDの状態から復旧する。複数既存契約の整理は層3へ回す。

**層2: 開いているCheckoutを1枚に保つ。**

| 選択肢 | 挙動 | 判断 |
|---|---|---|
| A（推奨） | pending IDをretrieveし、openなら同じURLを返す | Stripe作成回数を増やさず、失効と支払完了の競合を避ける |
| B | 古いopenをexpireして終了確認後に作り直す | API呼出と競合が増える。今回は不採用推奨 |

- completeなら契約を同期して409。支払処理中で有料資格を確認できなければ処理中の案内とし、completeだけで有料化しない。expiredなら新規作成へ進みpending IDを更新する。取得失敗なら新規作成しない。
- **初回同時要求への対策:** DBの短い予約RPCでプロフィールactiveを確認し、checkout_requestを一つだけ確定する。要求のplan/price/expires_at/return URL等は予約時点で固定し、全再試行が同じStripeパラメータ・同じ冪等キーを使う。別プラン要求が来ても先行予約を書き換えない。open中は同じセッションのプランを利用し、別プランへ変更するには期限終了後に再選択する旨を案内する。
- Stripe作成後、予約キー一致を条件にsession IDを保存してからURLを返す。作成後・DB保存前に中断しても、同じ予約から同じキーで結果を回収する。31分のexpires_atを毎回再計算して同じキーに違う値を渡さない。
- 予約を時計だけで捨てて別キーを作らない。結果不明はCustomerのSession一覧・予約metadata等で照合し、Stripe側の終了が確認できた時だけ更新する。冪等キーの保持期限を過ぎた要求は作り直さず要確認とする。[Stripeの冪等リクエスト](https://docs.stripe.com/api/idempotent_requests)
- Customer作成も利用者＋環境に対応する安定キーと固定パラメータを使う。DB insert競合時は勝者の行を読み直す。Customer作成だけ済んで利用者が退会した場合はセッションを作らず、未使用Customerの運用整理へ回す。
- open Sessionの失効は状態確認が必要で、支払い完了と競合した場合は再取得へ戻す。[Checkout Sessionの失効](https://docs.stripe.com/api/checkout/sessions/expire)

**層3: それでも二重に成立したら新しい方を止める。** checkout.session.completedで同じCustomerの稼働契約を全ページ照会する。複数ならStripeの契約createdが新しい方から即cancelし、最古の正当な契約を残す。通知の到着順を新旧判断に使わない。同秒の場合は契約IDによる一定の順序で残す1本を決め、すべての処理が同じ結論にする（ID順を実際の発生順とは主張しない）。Customerがこのアプリ専用であることと対象Price/metadataを検査し、別用途の契約を自動停止しない。

新しい契約を止めた印として該当stripe_events.needs_review=trueを保存し、cancelの成功/既終了を確認してから残す契約を同期・processed_atを確定する。cancel失敗は500で再送待ち。停止後にDB保存が失敗しても、再送で契約状態を照合でき、要確認の印が失われない順序で記録する。識別不能な契約は新規Checkoutを止めて要確認とする。

**自動キャンセルは既に成立した支払いの返金ではない。** 二重分の初回請求が発生する可能性は残り、Stripeダッシュボードで人が返金要否を確認する。自動返金・送金コードは作らない。[Stripeの契約キャンセル](https://docs.stripe.com/api/subscriptions/cancel)

### 3.4 退会と契約停止（I25・Q2）

現状はmypageからwithdraw_accountを直接呼び、ログイン停止に進む。Stripe契約の停止もサーバー側の退会拒否もない。新Checkoutはactiveプロフィール条件があるが、すでに存在する契約や発行済みSessionには効かない。

| 選択肢 | 利用者の体験・停止条件 | 規模・推奨 |
|---|---|---|
| A: 先に解約を求める | 既存のプラン解約で更新を止め、契約が実際に終了した後に退会する。cancel_at_period_end=trueだけでは退会を許可しない | **S（相対的な局所変更、推奨）**。有料期間中の即時退会はできない |
| B: 退会時に自動停止 | サーバーで退会要求を受け、新Checkout/resumeを遮断し、open Session失効・契約即時停止を確認して退会確定 | **M**。専用の退会Edge入口と退会要求状態が追加で必要。即時退会を重視する場合 |

Aでも画面の案内だけにはしない。withdraw_accountのDB処理は、プロフィール行→契約行の順にロックし、稼働契約/未解決checkout_request/pending Sessionがあれば拒否する。課金行があれば、Stripe照合でのみ設定するstripe_terminal_confirmed_atも必要とし、ローカルの期限切れや移行前のcanceledを終了証拠にしない。新規作成予約・稼働契約の同期時にはこの証拠を必ず消す。課金履歴がない会員は通常どおり退会可能。終了反映が遅れていれば契約画面でサーバー照合後に再試行できるようにする。

Checkoutの予約も同じプロフィール/契約ロック順とactive確認を使う。退会が先なら予約を拒否し、予約が先なら退会を拒否する。Stripeから結果が戻るまでDBロックを保持しない。cancelのresumeはactiveプロフィールでのみ受け付け、終了済み契約に対する操作はStripe側の失敗を成功扱いしない。退会済みへの遅延webhookは有料資格を復活させず、残存稼働契約なら停止・要確認へ進める。

Aの代償は「解約予約しても満了まで退会できない」こと。単に解約予約済みなら退会可とする小さなUI修正では、遅延resumeと継続請求を防げない。Bを採用する場合は専用入口、直接RPCの迂回防止、最小の退会要求列、失敗後の本人再試行まで同じ提案の改訂として確定し、新規worker等は持ち込まない。

**強制退会・既退会者は別途確認が必要:** 既にログインできない会員はAの自己解約を使えないため、公開前に運営がStripe上の契約残存を照合する。緊急の利用停止を課金停止待ちで遅らせず、停止対象と未処理の課金を必ず追跡する運用が必要。管理者の強制退会経路まで自動化するなら変更範囲が増えるため追加設計を提示し、Aだけで全退会経路が解決したとは報告しない。今回データ照合・停止・返金は実行しない。

### 3.5 invoice.payment_failed（I34）は取り込む

既存webhook内の変更で収まり、subscription.updated登録漏れ時の補完になるため取り込む。Invoiceから対象契約を特定して現在状態をretrieveし、§3.1/§3.2へ通す。失敗通知の名前だけでpast_dueに固定しない。支払成功後に遅着した失敗通知でもStripeの現在activeを維持する。契約なしの単発請求は明確な対象外、アプリの定期契約なのに対応が解決できなければ500＋needs_review。実装時はリポジトリ固定のStripe SDK/API版でInvoiceの参照形を確認する。

### 3.6 今後の拡張案（今回不採用）

### 9.2 `stripe-webhook/index.ts`（I06・I07・I34）

**現状の見落とし（今回の照合で発見）**: 現在のコード（209-227行）は「`stripe_events` への insert 成功＝未処理」を冪等性の判定に使い、失敗時は行を **delete** して再送に備えている。これは一見安全に見えるが、同じ event.id が輻輳配送（Stripeが前回の応答待ちでタイムアウトし、そのまま再送する）された場合に事故る: 1本目が処理中に2本目が届くと2本目は insert 重複で即 `200 duplicate:true` を返す→Stripeはそれで満足し再送しない→その後1本目が失敗して行を delete →**どこにも記録が残らないまま「処理済み」とStripeに伝えてしまう**。`processed_at` はこの穴をふさぐために必須。

1. **記録**: `insert` は `processed_at` を入れない（NULLのまま）。**delete は廃止する**（225行の`.delete()`を削除）。

   - 条件不一致による0件更新は正常（例外にしない）。UPDATE自体のDBエラーは500を返す。このとき5に進まないので `processed_at` はNULLのままで、Stripeの再送で7からやり直せる。

### 9.3 `stripe-checkout/index.ts`（I23・I24・I26）

1. **旧契約停止の失敗を握りつぶさない（I26）**: 124-134行の `catch` は現在「継続」している。これを、`stripe.subscriptions.cancel` が失敗した場合は `retrieve` で現在状態を確認し、`canceled` 等の終了状態を確認できなければ**新規Checkoutを作らずに中断**（500 or 409 相当＋日本語message）するよう変更する。
2. **開いているCheckoutの再利用（層2・I23）**: 既存行に `pending_checkout_session_id` が入っていれば、まず `stripe.checkout.sessions.retrieve` する。`open` なら同じ `session.url` を返して終了。`complete` なら `syncSubscription` 相当で同期し、9.2-7と同じ条件付きUPDATEでpendingをNULLに戻してから `409 already_subscribed`。ただしそのSessionの契約がStripe上で終了済み（9.2-7の例外）なら、pendingをNULLに戻して `expired` と同じく次へ進む。`expired` なら `pending_checkout_session_id` をNULLに戻して次へ進む。
3. **予約→作成→確定の3段階（I23・I24）**: 新規作成前に、条件付きUPDATEで自分の行を「予約」する。

   ```ts
   const claimToken = `reserving:${crypto.randomUUID()}`;
   const { data: claimed } = await admin.from('subscriptions')
     .update({ pending_checkout_session_id: claimToken, updated_at: new Date().toISOString() })
     .eq('user_id', user.id)
     .or(`pending_checkout_session_id.is.null,and(pending_checkout_session_id.like.reserving:*,updated_at.lt.${twoMinutesAgoIso})`)
     .select('user_id')
     .maybeSingle();
   ```

   `like` のワイルドカードは `*` で書く。`*` はPostgRESTが `%` の別名として公式に扱う記号。supabase-jsは `%` もエンコードするので `%` でも動くが、URLを直接書いたときにエンコードの取り違えが起きないよう `*` に統一する。値にリテラルの `*` は使えないが、claimTokenは `reserving:`＋UUIDなので該当しない。
   `claimed` が null なら「他の予約が進行中」＝処理中メッセージで409/425を返す（新規Customer作成・Checkout作成はしない）。既存行が無い新規顧客は、`insert` に `pending_checkout_session_id: claimToken` を含め、23505（PK競合＝ほぼ同時に別リクエストが同じユーザーで先にinsertした）を検知したら上記の条件付きUPDATE側にフォールバックする（**これがCustomer二重作成対策＝I24**。負けた側はStripe Customerを作らない）。
   Stripe Customer作成・Checkout Session作成が成功したら、`pending_checkout_session_id: session.id` で確定UPDATE（`.eq('pending_checkout_session_id', claimToken)` を条件に含め、確定できるのは予約者本人のみにする）。**2分を超えて `reserving:` のまま放置された行は次のリクエストが引き継げる**（cronやworkerを新設しない、というQ1/決定の前提どおり）。
4. **層1のStripe事前照合**: §3.3の設計どおり、Checkout作成前に `stripe.subscriptions.list({ customer, status: 'all' })` を全ページ取得し、active/trialingなら409、incompleteなら再作成しない、という判定を追加する（現状は104-117行のDB内 `existing` チェックのみで、Stripe側の実態は見ていない）。

### 9.4 `stripe-cancel/index.ts`

**変更: Stripeで契約が終了済みなら、DBをStripeの現在値に同期してから応答する。** 画面から呼べるよう、同期だけを行う入口も足す。

**理由**: 現行の期限掃除（`expire_stale_subscriptions` 179-183行）が canceled に書き換えるのは active/trialing だけ。past_due/unpaid 等は今でも、`customer.subscription.deleted` を取りこぼすとそのまま残る。9.5-1の退会ガードを入れると、この行は退会できなくなる。9.5-2で期限掃除がstatusを書き換えなくなるので、active/trialing も期限後にそのまま残るようになる。一方、現行コードは69-75行の `stripe.subscriptions.update` が失敗すると一律500を返す。終了済みの契約はStripeが更新を拒否するので、この組み合わせでは**退会（9.5のガードで拒否）も解約（常に500）もできなくなる**。

1. **同期専用の入口 `{ refresh: true }` を足す**（Stripeの契約は一切変更しない）。固着した行は画面が `payment_trouble`（past_due等）または `none`（期限切れのactive）になり、解約ボタンが出ない（`subscription.tsx` の296行・322行）。そのため9.6-1の退会画面から、この入口を呼ぶ。
   - 照会・同期に成功した場合の応答は常に `200 { ok: true, ended, pendingCleared }` で、409は返さない。画面側でエラーの本文を読まずに判定できるようにするため。`ended` は「DBの契約が終了済みになった（または元から終了済み）」ならtrue、稼働中ならfalse、契約IDが無い行ならnull。Stripe照会の失敗、DBの失敗、別の稼働契約の検出は500を返し、画面は9.6-1の「エラー」として扱う（再試行しない）。
   - `refresh` は59-61行（契約IDなし→404）と62-64行（DBが終了済み→409）を通らない。pending照合の後、契約IDが無い（または行が無い）なら `ended: null`、DBがすでに `canceled` / `incomplete_expired` なら Stripeの契約を照会せず `ended: true` を返す。2〜4を通るのは、DBが稼働中のstatusの行だけ。
   - **pendingも照合する**（2〜4より先に行う。59-61行の「契約IDなし→404」より前に置く）: DBの `pending_checkout_session_id` が `cs_` 始まりなら `stripe.checkout.sessions.retrieve` する。`expired` なら `.eq('pending_checkout_session_id', その値)` でNULLに戻す。`complete` なら9.2-7と同じ条件（例外を含む）で消す。`open` なら残す。照会失敗は500。`reserving:` は触らない。1件消せたら `pendingCleared: true`。expired通知の取りこぼしで、支払っていない会員が退会できなくなるのを防ぐ。
2. **終了の確認**: `refresh` のとき、および既存の解約/取消で69-75行の update が失敗したときは、即500にせず `stripe.subscriptions.retrieve(row.stripe_subscription_id)` を呼ぶ。
   - **`status` が `canceled` / `incomplete_expired`** → 3へ。
   - **`resource_missing`（契約IDがStripeに存在しない）**: テスト/本番キーの取り違えでも同じエラーになるため、これだけで終了とはみなさない。同じキーで `stripe.customers.retrieve(row.stripe_customer_id)` が成功した場合だけ3へ（3で、その契約IDがCustomerの一覧に無いことも確認する）。確認できなければ500のまま（DBは変えない）。
   - **それ以外（まだ稼働中）**: `refresh` ならDBの契約を変えずに `ended: false` を返す。update が失敗した場合は現行どおり500。
3. **Customer全体の確認**: `stripe.subscriptions.list({ customer: row.stripe_customer_id, status: 'all' })` を全ページ取得する。同じCustomerに active/trialing/past_due/unpaid/incomplete/paused の契約が1件でもあれば、DBを canceled にしない。DBの記録が抜けている稼働契約がある疑いがあるので、DBを変えずに500を返し、運営が確認できるようログに残す。1件も無いときだけ4へ。
4. **同期**: `status`（`resource_missing` のときは `canceled`）・`cancel_at_period_end`・`current_period_end`・`last_event_created`・`updated_at` を1文のUPDATEで書く。
   - 条件は `.eq('user_id', user.id).eq('stripe_subscription_id', row.stripe_subscription_id)`。その間にwebhookが別契約へ切り替えていたら上書きしない。これに `.or('last_event_created.is.null,last_event_created.lte.<書く値>')` を加え、`.select('user_id')` で更新件数を取る。
   - `last_event_created` にはretrieve直後の現在時刻（秒）を入れる。それまでに作られた通知はすべてこの値以下になるので、遅れて届いた古い past_due 通知は9.2-4の順序ガードで止まる。条件付きの1文にすることで、読み取りから書き込みまでの間に新しい通知が書いた値を小さい値で上書きしない。
   - DBエラーは500。0件なら行を読み直し、canceled/incomplete_expired になっていれば「終了済み」として扱い、そうでなければ500（「時間をおいてお試しください」）。**同期できていないのに終了済みと返さない。**
   - 終了済みのときの応答: 解約/取消の失敗経路では `409 already_canceled`（「このプランはすでに終了しています。」、62-64行と同じ文言）、`refresh` では `ended: true`。
   - 53-57行のselectと `SubscriptionRow`（23-28行）に `stripe_customer_id` と `pending_checkout_session_id` を足す。
5. 同期後の status は canceled なので、pendingが残っていなければ9.5の退会ガードを通過できる。これは期限掃除の推測ではなく、Stripeへの照会で終了を確認した結果に基づく。終了済み契約への解約/取消を成功（`ok: true`）とは返さない（§3.4）。`refresh` の `ok: true` は照会が成功したという意味で、契約の操作ではない。
6. **デプロイ順**: 現行の stripe-cancel は `resume === true` 以外をすべて解約予約として扱う（44-51行・69-71行）。9.4を反映する前の関数に `{ refresh: true }` が届くと、稼働中の契約に解約予約を立ててしまう。このため**stripe-cancel（9.4）を画面（9.6-1）より先にデプロイし、関数だけを旧版に戻すことはしない**。

`resume`（解約取り消し）は解約予約中のactive契約にだけ意味がある。その間は、Checkout側が110-117行の `stillValid` と9.3-4の層1で409を返すため、予約中Checkoutと競合しない。追加ガードは不要と判断する。

### 9.5 退会・期限掃除（I25・既存の整合修正）

`supabase/migrations/20260730120000_retention_and_anonymization.sql` の `withdraw_account`（159-171行）と、`20260811100000_m7_1_stripe_subscriptions.sql` の `expire_stale_subscriptions`（173-194行）を対象に、新migrationで `create or replace` する。

1. **`withdraw_account` にガードを追加（Q2=A）**:

   ```sql
   create or replace function public.withdraw_account()
   returns jsonb
   language plpgsql volatile security definer set search_path = public as $$
   declare
     sub record;
   begin
     select status, pending_checkout_session_id into sub
       from subscriptions where user_id = auth.uid();

     if sub.status in ('active','trialing','past_due','incomplete','unpaid','paused') then
       raise exception 'subscription_active';
     end if;
     if sub.pending_checkout_session_id is not null then
       raise exception 'checkout_pending';
     end if;

     update profiles set status = 'withdrawn', withdrawn_at = now()
     where id = auth.uid() and status <> 'withdrawn';
     if not found then
       raise exception 'not_registered';
     end if;
     perform public._record_withdrawal(auth.uid(), false, null);
     return jsonb_build_object('ok', true);
   end;
   $$;
   ```

   課金履歴が無い会員（`subscriptions` 行が無い、または `status='canceled'`）は従来どおり即座に退会できる。

2. **`expire_stale_subscriptions` から `status` の書き換えを外す**: 現在の179-183行（`status='canceled'` への強制変更）は、**Stripeが確認していない「終了」をDBに書き込む**行為であり、上記1のガード（`canceled` は退会許可対象）と組み合わせると「実際はStripeでpast_due継続中なのに3日で退会できてしまう」抜け道になる（今回の照合で発見）。この節は `profiles.subscription_active` の再同期（186-189行）だけ残し、`status` の書き換えは削除する。表示への影響は9.6参照。

### 9.6 画面（`mypage.tsx`・`subscription.tsx`）
