# advisor-design — センシティブ領域・土台判断の設計書づくり（全AI共通の手順）

> 全AI共通の正本。Claude Code は `/advisor-design`（`.claude/commands/advisor-design.md`）、Codex はスキル `advisor-design`（`.agents/skills/advisor-design/`）からこの本文を読み込む（AGENTS.md §12・§13-3）。
> **暫定版（2026-09-24）**: オーナーのPCの個人設定にある原本（`/advisor-design`）をクラウドから読めなかったため、feature・selfreview・AGENTS.md の記述から組み立てた。セットアップ（`docs/handoff/2026-09-24_multi-agent-setup.md` 手順4）で原本を取り込み、この本文を置き換える。原本と食い違う場合は原本を優先する。
> 「依頼内容」＝オーナーが伝えた、実装したい機能。

## 0. 役割と前提

- あなたは、センシティブ領域（AGENTS.md §6）または土台判断（DBスキーマ・認証モデル・権限モデル・データの持ち方）に触れる依頼の**設計担当**です。feature の手順（`docs/workflows/feature.md` §0）から回されてきます
- **上位モデルで実行する**（AGENTS.md §10）。下位モデルで起動されたと分かったら、冒頭でその旨を警告して止まる
- **実装しない。** 成果物は設計書だけ。コード・migration・設定は変更しない

## 1. 設計を書く前に調べること

1. `AGENTS.md`（開発憲法）の §4（提案の型）・§6（センシティブ領域）・§7（禁止事項）
2. `SPEC.md` と、関係する既存の設計書（`docs/design/`）・決定記録（`docs/decisions/`）
3. **実コードを自分で読む**。既存の設計書や他のAIの説明をうのみにしない（関係する migration・RLS・security definer 関数・Edge Function・画面）
4. `docs/review/AUDIT_CHECKLIST.md` の §A（壊れやすい「背骨」）と §C（調査済みの棄却リスト）
5. 同じ領域の既知の指摘（例: `docs/review/2026-09-24_統合指摘表.md`）

## 2. 設計書の作り方

ファイル `docs/design/YYYY-MM-DD_<内容>_設計提案.md` を新規作成する（例: `docs/design/2026-09-24_決済修正設計提案.md`・`docs/design/photo_ai_moderation_proposal.md`）。構成は AGENTS.md §4 の型に合わせる:

1. **目的** — 何を・なぜ作るか。依頼の解釈を書く（ズレていたらオーナーが訂正する）
2. **変更範囲** — 触るファイル・テーブル・Edge Function の一覧と規模（S/M/L）。最小構成で
3. **設計方針** — 判断が分かれる点ごとに「選択肢A/B＋推奨案と理由」
4. **リスクレベル** — センシティブ領域は自動的に「高」
5. **リスク・副作用** — 既存機能・既存データ・セキュリティへの影響。悪用シナリオ（認証済みの利用者Aが、ブロックした/退会した/接点のない利用者Bの何を読み・書き・追跡できてしまうか）と、その防ぎ方
6. **動作確認方法** — オーナーが実行できる手順を、受け入れ条件として書く。正常系と「失敗すべきケース」の両方
7. **確認質問** — 最大3つ

あわせて次も書く:

- 元に戻す方法（migration を含む場合は、戻す手順とデータへの影響）
- 人間レビューの段階（AGENTS.md §9）と、公開前に専門家に必ず見てほしい点

## 3. 終わったら

- 設計書だけをコミットする（ブランチと作業ログのルールは AGENTS.md §13）
- オーナーに、設計書のパス・推奨案の要約（3行以内）・確認質問を伝えて止まる
- 承認されたら、決定内容を `docs/decisions/` に記録する（AGENTS.md §8）。実装は feature の手順に戻って行う（オーナーが「設計に従って実装して」と伝える）
