## 背景

オーナーがミツモア（MongoDB→BigQuery→dbt構成）のDB設計知見をもとにした

## ⑤ タグの中間テーブル化を見送った理由（オーナー承認済み）

ミツモアの教訓は「①埋め込み配列と中間テーブルの**二重持ち**による不整合」と
「②**自由記述**による表記ゆれ」だが、ハピマリはどちらにも該当しない:

- タグは30個の**固定リストからの選択式**（自由記述ではない＝表記ゆれが構造上起きない）
- 表現は配列**1つだけ**で二重持ちしていない（不整合の発生源がない）
- 「このタグを持つ人」の抽出は **GINインデックス**で配列のまま高速に引ける（実測: Bitmap Index Scan）

中間テーブル化の実利がほぼ無い一方、相性計算・公開ビュー・検索・RLS・テストの改修が発生するため、
**マスタ表（辞書）＋不正値検証＋GINインデックス**で表記ゆれ・不正値を封じる方式を採用した。
※ 二重持ちはしない。関係の「正」は `profiles.value_tags` 配列であり、マスタは辞書。

## 実施した変更（migration `20260721110000_analytics_and_masters.sql`）

### 1. イベントログ `user_events`（後から取り返せない資産）

- append-only。`occurred_at / actor_id / event_type / target_user_id / match_id / props(jsonb)`
- **authenticated には読み書きとも一切の権限を与えない**（RLSポリシー無し＋GRANT無し）。分析は service_role のみ
- 書き込み経路は2つ:
  - **サーバー発（DBトリガ）**: like_sent / match_created / message_sent / call_logged /
    date_started / date_status_changed / report_created / block_created
    → **クライアント改修ゼロで確実に記録される**（アプリ側の実装漏れが起きない）
  - **クライアント発（RPC `log_user_event`）**: profile_view / discover_impression / filter_applied のみ許可。
    actor は常に `auth.uid()`（なりすまし不可）、props は2000文字上限
- 索引: occurred_at / (actor_id, occurred_at) / (event_type, occurred_at)
- BigQuery連携は行わない（まずPostgresに貯める。エクスポートは後からいつでも可能）

### 2. 状態遷移タイムスタンプ

- `date_proposals` に `intent_matched_at / first_proposed_at / confirmed_at / cancelled_at / done_at` と、
  **jsonb内から昇格した `date_on`（デート実施予定日）** を追加。既存行はバックフィル済み
- 記録は **BEFORE UPDATE トリガ**で自動スタンプ（既存のRPC 5本には手を入れない＝最小変更）
- matches / likes は `created_at` が matched_at / liked_at 相当のため列追加なし

### 3. マスタ表＋検証＋GIN

- `value_tag_master`（30件）/ `available_time_master`（4件）。辞書の正本は TS 側（`value_tags.ts` / `constants.ts`）
  → **タグを増やす時は TS とマスタの両方に追加すること**
- profiles の BEFORE INSERT/UPDATE トリガでマスタ外の値を拒否（`unknown_value_tag` / `unknown_available_time`）
- `value_tags` / `available_times` に GIN インデックス

### 4. 小粒

- `profiles.email_bounced`（将来のメール運用向け）
- 索引補強: likes(from_user, created_at) / blocks(blocked) / profiles(status, gender, birth_date)
- 新規テーブルから `TRUNCATE / REFERENCES / TRIGGER` を anon・authenticated から剥奪

### クライアント側

- `apps/mobile/src/lib/analytics.ts`（fire-and-forget の `logEvent`）
- profile詳細画面で `profile_view` を記録（クライアントしか知り得ない行動のため）

## 別途報告した既知の指摘（未対応・要判断）

**`public` スキーマの全テーブルで anon・authenticated に `TRUNCATE` が付いている**
（Supabaseのデフォルト権限由来。TRUNCATE は RLS を迂回する）。
PostgREST に TRUNCATE のエンドポイントが無いため API 経由の実害は無いが、多層防御としては穴。
本migrationでは**新規3テーブルのみ剥奪**し、既存13テーブルは承認待ちとした。
修正は1行（`revoke truncate on all tables in schema public from anon, authenticated;`）。
