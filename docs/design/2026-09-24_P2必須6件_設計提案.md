### 設計（最終差分）

**方式の選択: SECURITY INVOKER（推奨・採用）＋関数内の当事者条件（必須）**

用語: SECURITY INVOKER は、呼んだ本人の権限で動く関数。SECURITY DEFINER は、作成者（postgres）の権限で動き、RLS を素通りする関数。

| | INVOKER（採用） | DEFINER |
|---|---|---|
| 当事者の検証 | 既存の RLS（matches・messages）が必ず効く。そのうえで関数内の WHERE でも絞るので、守りが二重になる | 関数内の WHERE だけが頼り。書き誤ると他人の本文が漏れる |
| 将来 RLS を強めた場合 | 自動で追従する | 関数側を直し忘れると、一覧だけが古い条件のまま残る |
| 性能 | `is_match_participant` が、索引で取った候補1行ごとに呼ばれる。LIMIT 1 なので、およそマッチ数回 | 判定の呼び出しが無い分だけわずかに速い |

→ INVOKER を採る。「同等以上に守る」を構造で保証でき、DEFINER の利点は性能の小さな差だけのため。

language sql
stable
security invoker
set search_path = public
as $$
  select m.id, lm.body, lm.created_at
  from public.matches m
  cross join lateral (
    select msg.body, msg.created_at
    from public.messages msg
    where msg.match_id = m.id

  'メッセージ一覧のプレビュー用。呼び出し者のマッチごとに最新メッセージ1件（本文・時刻）を返す。INVOKERで既存RLSに従い、加えてWHEREで当事者に限定（RLSを素通りするロール向けの多層防御）。メッセージ0件のマッチは行を返さない';

grant execute on function public.get_my_latest_messages() to authenticated, service_role;

- **引数は無し。** 呼び出し者は `auth.uid()` で決まる。クライアントからマッチIDを渡させない（理由は「判断が分かれる点」1）。
- **`where m.user_a = auth.uid() or m.user_b = auth.uid()` は必須で、削ってはいけない。**
  - authenticated については RLS と同じ条件なので、`idx_matches_user_a` / `idx_matches_user_b`（`init.sql:131-132`）を使う実行計画に寄せる役目もある。

- **並び順は `order by msg.created_at desc` だけにする。**
  - 現行の PostgREST の `order=created_at.desc` と同じ（NULLS FIRST）。索引 `(match_id, created_at)` を逆向きにたどり、LIMIT 1 で先頭を取るだけの形になる。

- **REVOKE の必要性（ドラフトの説明を訂正）**
  - ローカルの `pg_default_acl` を見ると、postgres が public に作る関数の既定は `{postgres=X/postgres}` だけに見える。

- **Web 専用 SDK は使わない。** `supabase.rpc` はネイティブと Web で共通なので、`.web.ts` への分離は要らない。

### 判断が分かれる点

1. **RPC の引数**
   - A: 引数無し。`auth.uid()` から自分のマッチを導く。
   - B: `p_match_ids uuid[]` を受け取る。
   - **推奨 A。** 他人のマッチIDを入れる入口がそもそも無い。B でも RLS と WHERE が他人の行を落とすが、A のほうが攻撃面が小さい。現行の `.in()` は全マッチIDを URL に並べているので、URL が長くなる懸念も同時に消える。
2. **本文の返し方**
   - A: 全文を返し、30字の切り詰めは画面側（168行）に残す。
   - B: DB 側で `left(body, 30)` にしてから返す。
   - **推奨 A。** 表示が現状と完全に同じで、文字数の仕様を変えても migration が要らない。転送量は「最大2000字（`init.sql:77`）× マッチ数」で、現行の全メッセージ転送より大幅に少ない。
3. **テストの置き場所**
   - A: I08 専用の新しいスイート。
   - B: P2 の各項目と共通の1スイート。
   - **推奨 A。** 期待 PASS 件数を項目ごとに管理でき、並行実装のときの衝突が `SUITES` の1行追加で済む。

service_role への GRANT は、既存の流儀に揃えて付与すると確定した。無害であることは WHERE 行とテスト #11 で担保するので、分岐として残さない。

### リスク・副作用・限界

- **既存機能への影響**
  - マイク拒否・15分切断（timeout）・相手の拒否・無応答・通話中の切断・通信断は、これまでどおり固定文言を表示し、2秒後に自動で戻る。

  - ネイティブ（モック）は `agora-token` を呼ばないので、案内の表示は変わらない。ボタンを消す条件とキャッシュキーの分離は、ネイティブにも効く。

- **既存データ・DB・性能**: 影響なし。
- **案内の表示時間**: 推奨Aでは、サーバーの案内が出ている間は利用者が「チャットへ戻る」を押す必要がある。
- **今回保証しないこと**
  - (a) マイク許可の確認がトークン取得より先に出ること（M8 の設計）。資格のない人にもマイクの確認が出る。マイクを拒否した場合、サーバー側の理由は表示されない。
  - (b) Agora に接続したあとの失敗（join の失敗、トークン期限切れ）の文言。
  - (c) 相手の状態が、画面を表示したあとで変わる行き違い。これはサーバーの拒否とその案内（条件6）で対応する。
  - (d) URL を直接開いた・再読込した通話画面では、戻り先の履歴がないため「チャットへ戻る」が効かない（既存の制約。追加の発見に記載）。

  - (g) 実際の音声の疎通。

### 判断が分かれる点

1. **送信者の判定を別関数に切り出すか**
   - **A（推奨）**: 上の設計どおり `validateLikeSender` を切り出す。Edge Function は今の #6 の位置でこれを呼び、validateLike も先頭でこれを呼ぶ。
   - B: Edge Function の直書き判定を消し、validateLike（L212）だけに任せる。
   - 推奨理由: B にすると、未確認の送信者が不正な toUser を送ったときや DB 障害時に、403 ではなく500が返る。未確認の送信者に対する DB 呼び出しも2回増える。つまり B はオーナー決定の「挙動は変えない」に反するので、実質的に選べない。A はこの条件を厳密に守れる。
2. **受信者が未確認でもいいねが届くことを、テストで固定するか**
   - **A（推奨）**: 固定する（追加テストの3件目）。現行挙動の回帰テストとして残す。
   - B: 固定しない。
   - 補足: 2026-08-26 の決定には「行政書士の回答次第で戻すのも各1行」とある（`:17`）。統合後は、ゲートを戻す場合も受信者までゲートする場合も、`like_rules.ts` の修正とあわせてテストの修正が必要になり、1行では済まない。ただし方針が変わったときにテストが赤くなるのは意図した動きなので、A で問題ない。
3. **「likes へ直接 INSERT できない」ことを SQL の回帰テストとして足すか**
   - **B（推奨）**: 足さない。既存の `scripts/*.sql` にもこのテストは1件も無い（`test_review2_fixes.sql:306-307` と `test_m67_retention.sql:34` は、superuser として INSERT するテスト準備）。今回は DB を変えないうえ、決定の範囲（`like_rules.test.ts` への追加）を超える。代わりに受け入れ条件7で一度だけ手で確認する。
   - A: 足す。この場合は `run_sql_tests.sh` の期待件数の更新も変更範囲に入る。

## I11 — 写真の閲覧者在籍条件（退会・凍結・プロフィール未作成の人が他人の写真を読める経路を潰す）

**オーナー決定:** A案（`docs/decisions/2026-09-24_レビュー残件20件の方針決定.md:21`）。写真の判定関数と Storage ポリシーの両方に「閲覧者が在籍中」の条件を追加する。オーナーの追加指示は次の3点。
1. 退会・凍結した人が他人の写真を読める経路は完全に潰す。
2. 本人の未承認写真のプレビューは維持する。
3. 発行済みの署名URL（期限つきで写真を見られるURL）の即時失効は別の問題として扱い、そのことを受け入れ条件に明記する。

本人フォルダの扱いは旧提案 R06 で「本人の写真まで非activeで遮断する変更は分ける」と整理済み（`docs/design/2026-09-21_Codexレビュー15件_修正設計提案.md:193`）。今回はこの結論をそのまま使う。

### 現状と根拠

- **「在籍中」の定義**
  - `profiles.status` が取る値は `active` / `suspended`（凍結）/ `withdrawn`（退会）の3つだけ（`supabase/migrations/20260705100000_init.sql:30`）。既定値は `'active'`（ローカルDBで確認）。
  - 匿名化済みの人も status は `withdrawn` のまま。`anonymized_at` 列が別にあるだけ（`20260730120000_retention_and_anonymization.sql:22`）。
  - `is_caller_active()` が true になるのは「自分の profiles 行があり、`status='active'`」のときだけ（`20260730100000_m6_6_audit_fixes.sql:20-28`、snapshot `schema.generated.sql:1025-1032`）。
  - したがって、凍結・退会・匿名化済み・プロフィール未作成（オンボーディング途中）の人はすべて false になる。本人確認済みかどうか（is_verified）は判定に入らない。
- **穴1: Storage の読み取りポリシー**
  - `storage.objects` の SELECT ポリシー（RLS＝行単位のアクセス制御）の条件は「本人フォルダ OR `is_photo_visible_to(name)`」だけ（`m6_6_audit_fixes.sql:209-219`、snapshot `:3674`）。
  - `is_photo_visible_to` が見ているのは「承認済み」「持ち主が active」「ブロックなし」の3点だけで、閲覧者が在籍しているかは見ていない（`m6_6:194-205`、snapshot `:1100-1113`）。
- **穴2: 直接呼べる判定関数**
  - `is_photo_of_profile` も閲覧者の在籍を見ていない（`20260902100000_review2_security_fixes.sql:100-111`）。
  - 2関数とも、ログイン済みの利用者（authenticated）が RPC で直接実行できる（`review2:113-114`、`m6_6:206-207`、ローカルDBの proacl でも確認）。
- **実測（ローカルDB、`begin read only` の SELECT のみ）**

### 判断が分かれる点

「凍結・退会した本人が自分のフォルダを読めるか」は決定の範囲内で結論が出ている（読める。R06 `:193` とオーナー指示2のため）。そのうえで細部として残るのは次の3点。

   - B: 新しい名前にする。
   - A を推奨する理由: 61バイトなら切り詰めは起きない。snapshot の差分が USING 式だけで済み、`if exists` を付けない drop で名前の取り違えを migration の失敗として検出できる。
2. **テストの置き場所**
   - A（推奨）: 新しいスイートに分ける。
   - B: `test_m66_audit_fixes.sql` の #4 に追記し、期待件数を17から38にする。

3. **HTTP 経由（実際の Storage API）の確認**

### 受け入れ条件

1. 凍結（`status='suspended'`）した利用者の JWT で、他人の承認済み写真に対して次の操作をすると、すべて失敗するか0件になる。
   - `storage.objects` の SELECT → 0行
   - `POST /storage/v1/object/sign/photos/<他人のパス>` → エラーになり、署名URLは返らない
   - `GET /storage/v1/object/authenticated/photos/<他人のパス>` → エラー
   - `GET /storage/v1/object/info/authenticated/photos/<他人のパス>` → エラー
   - `POST /storage/v1/object/list/photos`（prefix `<他人のUID>/`）→ 0件
   - `POST /storage/v1/object/copy`（sourceKey に他人のパス、destinationKey に自分のフォルダ）→ エラー

## I28 — ブロック判定が取れないとき（error あり／boolean でない）は通話トークンを発行しない

**オーナー決定:** A 案（docs/decisions/2026-09-24_レビュー残件20件の方針決定.md:22）。ブロック判定が取れないとき（RPC が error を返した、または結果が true/false のどちらでもない）は、トークンを発行しない。発行へ進むのは `data === false` のときだけ。`true` のときは従来どおり 403 `blocked` を返す。

### 現状と根拠

- `supabase/functions/agora-token/index.ts:137-140` は `const { data: blocked } = await admin.rpc('is_match_blocked', { target_match: matchId });` と書かれていて、**error を受け取っていない**。拒否するのは `blocked === true` のときだけ。RPC が失敗すると `data=null` になり、`null === true` は偽なので、トークン生成（164-172行 `RtcTokenBuilder.buildTokenWithUserAccount`、生成箇所はここ1か所だけ）までそのまま進む。つまり判定が失敗している間は、ブロック済みの2人にも通話の入場券（トークン）が出る。障害時に「許可」側へ倒れる fail-open の状態になっている。
- この行は M8 実装（80faa9f）と本人確認ゲートの追加（f2723d4）以降、一度も変わっていない。
- 呼んでいる RPC と実行ロールは次のとおり。
  - 関数は `public.is_match_blocked(target_match uuid) returns boolean`。SECURITY DEFINER で、`search_path=public` に固定されている。
  - 本体は `select exists(... public.is_blocked_between(m.user_a, m.user_b))`（migration `supabase/migrations/20260712130000_m6_5_security_p1.sql:57-67`、snapshot `supabase/schema.generated.sql:1038-1047`、ACL は :3904-3906）。
  - 呼び出しは `adminClient()`（index.ts:62-69。`SUPABASE_SERVICE_ROLE_KEY` を使い、オプション指定なし）経由なので、**service_role**（サーバー用の全権ロール）で実行される。
  - migration・snapshot・起動中のローカル DB の pg_proc の3つを照合し、一致していることを確認した。pg_proc は SELECT のみで確認し、proacl={postgres, authenticated, service_role}、戻り値 boolean、prosecdef=t、proconfig={search_path=public}、同名の関数は1つだけ。
- 現在の本体は `exists` なので、正常に動けば必ず true か false を返す。ただし I29 で本体を「当事者限定」に作り替えたとき、service_role の経路で NULL を返したり例外を投げたりすると、**今のコードでは黙って発行側に倒れる**。I28 は、この事故を防ぐ防波堤にもなる。
- supabase-js（中の postgrest-js）は、`throwOnError` を指定しなければ、通信断のような fetch の失敗でも例外を投げない。代わりに `{ data:null, error:{ code:'' ... } }` を返す。そのため現状では、通信断も「null＝許可」の経路を通る。
- 手本にする既存実装は `supabase/functions/like/index.ts:200-210`。`blockedError` を見て 500 `internal` を返している（ただし boolean かどうかは見ていない。extra_findings を参照）。

同じファイルの他の資格チェックも「error を見ずに進む」パターンかどうかを確認した。

| 箇所 | error の扱い | 判定が取れないときの結果 | 評価 |
|---|---|---|---|
| `authenticate` index.ts:71-80 | `error \|\| !user` なら null → 401 | 拒否 | 問題なし |

/**
 * 通話トークン発行の判定のうち DB アクセスを伴わない部分（I28）。
 * agora-token/index.ts が import し、packages/shared/test から Vitest で検証する。

export type BlockCheckOutcome = 'clear' | 'blocked' | 'unavailable';

/**
 * is_match_blocked の RPC 結果を解釈する。error を最優先で見る。
 * false を確認できたときだけ clear。error あり・null・boolean 以外はすべて unavailable。
 */
export function interpretBlockCheck(result: {
  data: unknown;
  error: unknown;
}): BlockCheckOutcome {
  if (result.error != null) return 'unavailable';
  if (result.data === false) return 'clear';
  if (result.data === true) return 'blocked';
  return 'unavailable';
}

1. **拒否時の status と error code**

### リスク・副作用・限界

- **既存機能への影響**

- **性能**: 変化なし。照会の回数は同じ。
- **本番 deploy**
  - `_shared` 方式は stripe-* と同じなので、launch_checklist #23（packages/shared の同梱）には依存しない。
  - ただし `docs/release_web.md:37` の deploy コマンドに agora-token が入っていない（既存の不備。extra_findings を参照）。手順書どおりに deploy すると、この修正は本番に届かない。

- なお、スキーマの USAGE（中の名前を参照する権限）は作成時の名前解決でだけ要り、実行時は不要と見られる（未実測）。
- EXECUTE を与えると、旧提案 R09 の「認証利用者に直接の EXECUTE/USAGE を与えない」（`docs/design/2026-09-21_Codexレビュー15件_修正設計提案.md:247`）と、下記の T6-e に反する。変更範囲もビューと2ポリシーの作り直しに広がる。
- #1〜#3 は引数が常に呼び出し者本人なので、公開関数の当事者検査を必ず通る。挙動は変わらない。

  1. private の USAGE を所有者以外に与えない。
  2. 関数ごとに明示の REVOKE を書く。
  3. T6-e で検査する。

**(3) 公開 `is_blocked_between` の置換**
- 署名と引数名 `a`/`b` は維持する。like が名前付き引数で呼んでいるため。
- CREATE OR REPLACE なので OID（DB 内部の関数番号）と ACL は保たれる。ビューとポリシーは作り直さなくても新しい本体を使う。
```sql
create or replace function public.is_blocked_between(a uuid, b uuid)
returns boolean
language plpgsql stable security definer set search_path = ''
as $$
declare
  v_uid uuid := auth.uid();
begin
  -- blocks.blocker/blocked は NOT NULL（m3_social.sql:18-19）。NULL を含む組は常にブロックなし。
  -- service_role や Studio でビューを読んだとき（auth.uid() が NULL）に例外にしないため、先に判定する。
  if a is null or b is null then
    return false;
  end if;
  if v_uid is not null then
    if v_uid <> a and v_uid <> b then
      return false;          -- 第三者: blocks を読まずに false（有無と無関係＝区別不能）
    end if;
  elsif coalesce(auth.role(), '') <> 'service_role' then
    raise exception 'forbidden' using errcode = '42501';   -- 利用者でも service_role でもない
  end if;
  return exists (
    select 1 from public.blocks bl
    where (bl.blocker = a and bl.blocked = b) or (bl.blocker = b and bl.blocked = a)
  );
end;
$$;
revoke execute on function public.is_blocked_between(uuid, uuid) from public, anon;
grant execute on function public.is_blocked_between(uuid, uuid) to authenticated, service_role;
comment on function public.is_blocked_between(uuid, uuid) is
  'I29: 当事者(auth.uid()∈{a,b})と service_role だけが実判定を得る。第三者は常に false、身元なしは forbidden(42501)。SQL 内部からは private.is_blocked_between を使う';
```

declare
  v_uid uuid := auth.uid();

  if v_uid is null and coalesce(auth.role(), '') <> 'service_role' then

### 判断が分かれる点

1. **当事者でない利用者が呼んだときの戻り値**
   - A: false（ブロックなし・マッチ不存在と同じ値）
   - B: 例外
   - C: NULL
   - **推奨A。** 理由:
     - RLS の AND は評価の順番が保証されない。A なら順番に関係なく結果が同じで、途中で例外にならない（旧提案 R09 の `docs/design/2026-09-21_Codexレビュー15件_修正設計提案.md:245` の要求にも合う）。
     - B だと、非当事者の送信失敗が、実行計画しだいで「RLS 違反」と「forbidden」のどちらにもなる。
     - C は plpgsql の `if f() then` で「ブロックなし」扱いになって素通りし、型（`Returns: boolean`）も崩れる。
   - A の弱点: 将来、`not is_match_blocked()` を `is_match_participant` なしで書くと素通りする。関数コメントに「必ず AND で使う」と明記する。現行の2ポリシーは AND 済み（snapshot 3597, 3601）。
   - 身元なし（利用者でも service_role でもない）の呼び出しは、A でも例外にする。false にすると、service_role の判定が壊れたときに like や agora-token が「ブロックなし」で通ってしまうため。

2. **service_role の見分け方**
   - A: `auth.role() = 'service_role'`
   - B: A に加えて、`current_setting('role')` も見る
   - `current_user` は SECURITY DEFINER の中では常に所有者の postgres になるので使えない。`auth.uid() IS NULL` だけで許可することはしない（R09 :246）。
   - **推奨A。** 理由:
     - `auth.role()` は `request.jwt.claim.role` → `request.jwt.claims->>'role'` の順に読む（ローカル DB の関数定義で確認）。この値は、PostgREST が署名を検証した JWT（ログイン証明のデータ）から入れる。
     - 利用者が `set_config` を呼べる公開関数は無い。
     - B の前提（DEFINER の中で role の設定値が保たれるか）は未実測で、確実性が上がらない。

3. **公開 `is_blocked_between` の本体**
   - A: blocks を直接読む
   - B: private を呼ぶ
   - **推奨A。** B だと、ビューの1行ごとに入れ子の関数呼び出しが1回増える。同じ条件式が2か所に書かれることは、C08 で private の結果との一致を検査して補う。

4. **内部呼び出しの付け替え範囲**
   - A: DEFINER 4関数と `is_match_blocked` のすべて
   - B: `is_match_blocked` だけ
   - **推奨A。** 理由:
     - 決定の「内部判定は非公開へ」に合う。
     - B は、写真（1枚ごと）と測距という最も多く呼ばれる経路で、当事者検査の負荷を増やす。
     - B は、内部処理が `auth.uid()` の意味に依存し続ける。
   - A の代償: 写真の2関数が I11 と重なる。

5. **`private.is_blocked_between` の権限モデル**
   - A: SECURITY DEFINER＋`search_path=''`
   - B: SECURITY INVOKER、SET 句なし
   - B の利点: 本体を呼び出し元のクエリに展開する「インライン化」が可能になる。
   - **推奨A。** 理由:
     - プロジェクトの流儀と R09 :247（「SECURITY DEFINER の固定 search_path・明示スキーマ参照」）に合う。
     - 今回は実行計画を現状と同じに保ち、回帰のリスクを抑える。インライン化による高速化は I12（範囲外・低優先）で実測してから判断し、1行の CREATE OR REPLACE で切り替えられる。
   - なお、呼び出し元はすべて postgres が所有する DEFINER 関数なので、B でも動作は同じになる（postgres は blocks の所有者で、FORCE RLS も無い）。

### 受け入れ条件

1. F が M をブロックしている状態で、第三者 C が `is_blocked_between(F,M)` と `(F,M2)` を呼ぶと、両方 false（C04）。ブロックを削除した後に C が `(F,M)` を再び呼んでも false で、削除前の値と一致する（C20）。

   - F の `(F,M)` と、M の `(M,F)` は true。F の `(F,M2)` は false（C01〜C03）。
