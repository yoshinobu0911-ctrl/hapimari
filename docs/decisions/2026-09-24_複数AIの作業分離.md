# 2026-09-24: 複数AIの作業を「フォルダ・ブランチ・ファイル」で分ける

状態: **提案（オーナー承認待ち）**。ルールは `AGENTS.md` §12・§13、導入手順は `docs/handoff/2026-09-24_multi-agent-setup.md`

## 背景（点検で分かった事実）

オーナーからの依頼: 各AI（Claude Code / Codex / Grok）の作業や進捗がぶつからない（バッティングしない）フォルダ構成になっているか点検してほしい。続けて、`/advisor-design`・`/advisor-review` を Claude 以外のAIからも使えるようにし、各AIが主に編集するファイルを分けてほしい。
点検の対象は GitHub 上のリポジトリ。ローカルの未コミット変更・`C:\Users\haosh\dev\AGENTS.md`・PC の個人設定はクラウドから見えないため、導入手順の中でローカルの Claude Code が確認する。

良い点（今後も維持する）:

- 決定記録・レビュー記録は日付付き、migration は時刻付きのファイル名なので、ファイル名どうしは衝突しにくい
- 他のAIの成果物はファイル名にAI名が入っている（例: `2026-09-20_外部レビュー_codex.md`）
- apps/mobile・apps/admin・packages/shared・supabase の役割分けが明確

## 決めたいこと（提案）

1. **1つのAIセッション = 1つの作業フォルダ（git worktree）= 作業ごとに1つのブランチ**。本体フォルダは統合とオーナーの確認専用にする（§13-1・13-2）
2. **main への取り込みは Claude Code がレビューしてから行う**（merge commit に「どのAIの作業か」が残る）
3. **AIが主に編集するファイルをAIごとに分ける**（§13-3）: 作業ログは `docs/agents/<AI名>/log.md`、設定と入口は Claude=`.claude/`・Codex=`.agents/skills/`・Grok=`.grok/`。`progress.md` には統合時に1行要約だけを書く
4. **定型ワークフローの本文は `docs/workflows/` の1か所だけ**にし、各AIの入口は本文を読み込むだけにする（§12）。advisor-design・advisor-review もここに置き、全AIから使えるようにする
5. **`supabase/`（DB・Edge Function）と生成ファイルは同時に1つのAIだけ**。原則 Claude Code（§13-4）
6. コミットの最後の行に `Agent: <AI名>` を付ける。QUESTIONS.md の新しい番号は `Q-YYYYMMDD-<AI名>` にする

## 選択肢

作業場所の分け方:

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A. 時間で分ける | 今の1フォルダのまま、同時に動かすAIを1つに限る | 準備が要らない | 並行作業ができない。コミット忘れで混ざる問題（事実2）は残る |
| **B. 作業フォルダを分ける（推奨）** | AIごとに git worktree とブランチを使う | 同時に動かしてもファイルとコミットが混ざらない。履歴は1つなので統合が簡単 | フォルダごとに `pnpm install` と `.env` のコピーが必要。DBとポートは共有のまま（ルールで補う） |
| C. 丸ごと別コピー | AIごとにリポジトリを clone する | 仕組みが単純 | 統合のたびに GitHub 経由の push/fetch が必要 |
| D. GitHub の PR で統合 | 各AIがブランチを push し、PR で取り込む | CI とレビュー記録が残る | オーナーの操作が増える。B と組み合わせて後から導入できる |

定型ワークフローの共有のしかた:

| 案 | 内容 | 判断 |
|---|---|---|
| A. AIごとに全文を複製 | `.claude/commands/` と `.agents/skills/` に同じ本文を置く | 不採用。食い違う（事実8の削除理由そのもの） |
| **B. 共通の本文＋AIごとの薄い入口（推奨）** | 本文は `docs/workflows/`、入口は本文を読み込むだけ | 採用。本文の変更は1か所で済み、各AI専用の設定欄は各AIのフォルダで独立に持てる |
| C. AGENTS.md に全文を書く | 開発憲法に手順まで入れる | 不採用。憲法が長くなり、Codex の読み込み上限（32KiB）にも近づく |

進捗の記録のしかた:

| 案 | 内容 | 判断 |
|---|---|---|
| A. 今のまま | 全AIが `progress.md` に直接書く | 不採用。最多の衝突箇所（事実6） |
| **B. AIごとのログ＋統合時の要約（推奨）** | 詳細は `docs/agents/<AI名>/log.md`、`progress.md` は1行要約とリンク | 採用。AIどうしが同じ行に書かない。オーナーは引き続き `progress.md` で全体を見られる |

## 推奨案を選ぶ理由

- 事実1・2（同じフォルダで作業するので混ざる）を根本から防げるのは作業フォルダの分離だけ。worktree は履歴を共有するので、統合がローカルで完結する
- 本体フォルダは、オーナーの起動用 bat が指す場所のまま残せる（オーナーの操作の変化が小さい）
- 本文を1か所にすれば、事実8のような「複製の食い違い」が仕組みの上で起きない

## 残るリスク

- ローカルDBとポートは、フォルダを分けても共有のまま → `AGENTS.md` §13-1・13-4 のルールで運用する
- ルールを守るかどうかはAI次第 → 統合時に Claude Code がレビューして確認する（§13-2）
- advisor-design・advisor-review の本文は暫定版 → 導入手順4で PC の原本に置き換える

## 元に戻す方法

`git worktree remove <フォルダ>` で作業フォルダを消し、この提案の統合コミットを `git revert` すれば元の運用に戻る。退避した PC の個人設定や `.agents` は、`C:\Users\haosh\dev\_backup\2026-09-24_hapimari\` から元の場所へ戻す。
