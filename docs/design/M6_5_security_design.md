## 対応1: 位置情報の「三点測位」対策（両レビュアー指摘・最重要）

**攻撃**: 自分の位置を3回偽装して同じ相手との距離を測ると、交点で相手の自宅が特定できる。

**多層防御（3点セット）**:

1. **距離の帯域化+ペア固定ジッター（本命）**
   - `get_profile_distances` が返す値を「正確なkm」から**表示と同じ帯域（5km刻み・30km超は10km刻み）**に変更。
   - さらに**ペアごとに固定の誤差（±1.5km相当）**を距離に加えてから帯域化する。
     誤差はペアのID から決定的に計算（`hash(自分ID, 相手ID)`）するため、**何度測っても同じ値**
     ＝繰り返し測定による平均化で誤差を消す攻撃が効かない。
   - 効果: 三点測位しても数km四方までしか絞れず、自宅特定は不可能になる。
2. **位置更新の制限**（Leo案）: `set_my_location` に **30分に1回・1日8回まで**の制限
   （`profile_locations.updated_at` と日次カウンタで判定）。通常利用（アプリ起動時に1回）には影響なし。
3. **対象の限定**（さとまん案）: 距離を返す相手を「**active かつ 異性 かつ 非ブロック**」に限定
   （discover表示・詳細・マッチ相手はすべてこの範囲に収まる。ブロック済み相手の距離は取得不可に）。

## 対応2: 管理画面の認証（さとまん指摘・公開前必須）

- **Next.js middleware で Basic認証**（ID/パスワードは環境変数で設定・環境変数が無い場合は
  全リクエスト拒否）。ページも Server Action の POST も同じ middleware を通るため一括で守られる。
- 併せて各 Server Action 冒頭にも認証ヘッダ検証を入れる（二重化）。
- 本格的な管理者ログイン（Supabase Auth + 管理者テーブル）は M7 の「BEサーバー一枚挟む」
  構造変更と同時に実施（さとまんの推奨方向と一致）。

## 対応3: 写真の非公開化 + 事前審査（両レビュアー指摘）

1. **photos バケットを非公開化**。表示は**署名付きURL（有効期限1時間）**に全面切り替え。
2. `photo_urls` は「URL」ではなく**バケット内パス**を保持する形に移行
   （Leoの「悪意あるURLを仕込める」指摘もこれで同時に解消。既存データはSQLで一括変換）。
3. **写真の事前審査（人力・MVP方式）**: 新規アップロード写真は `photo_reviews` キューに入り、
   **管理画面で承認されるまで本人以外には表示されない**（他人からはプレースホルダ）。
   管理画面に「写真審査」ページを追加（本人確認審査と同じ操作感）。
   - ストア/公開審査で求められる「不適切画像対策」を外部API契約なしで満たす、現段階で最強の方式。
   - 会員が増えたら M7 でモデレーションAPI（Rekognition等・要オーナー契約）を前段に入れて
     自動承認化し、人力は目視ダブルチェックに縮小する。

## 対応4+6: 生年月日・子ども情報の秘匿（公開プロフィールのビュー化）

**方式**: `profiles_public` ビュー（security definer）を新設し、**他人のプロフィール取得を全てこのビュー経由に一本化**。

- ビューが公開するもの: ニックネーム・性別・**年齢（サーバー側で計算した整数。誕生日は出さない）**・
  居住地・結婚歴・結婚観・自己紹介・価値観タグ・会える時間帯・認証バッジ・写真パス
- ビューに**含めない**もの: `birth_date`（日付そのもの）・`has_children`・`children_living_together`・
  `ok_child_date`・`understands_children`・`understands_remarriage`・`subscription_active`
- `profiles` 本体の SELECT は「**本人の行のみ**」に変更（自分の設定表示・R9判定用）。
- discover の年齢絞り込みは birth_date 計算をやめ、ビューの `age` 列で直接絞る（コードも簡潔になる）。
- **相性スコアへの影響**: 他人の子ども・理解宣言データが取れなくなるため、「事情への理解（10%）」を
  相性計算から除き、残り（タグ50%・距離17%・時間帯17%・結婚観16%相当に再正規化）で評価する。
  R3廃止（子持ち配慮はしない）のオーナー方針とも整合する。

## 対応5: ブロックの全アクション遮断（Leo指摘）

ブロック済みペア間で以下をすべてDB層で拒否する（現状はプロフィール非表示のみ）:

- **メッセージ送信**（messages INSERTポリシーに非ブロック条件を追加）
- **通話記録**（calls INSERTポリシーに同上→通話ボタンも相手プロフィール不可視で自然に消える）
- **デートの相談**（date系RPCの当事者検証 `_date_get_match` に非ブロック条件を追加）
- いいね（Edge Function）は既にブロック検証済み・変更なし

実装は共通ヘルパ `is_match_blocked(match_id)` を1つ作り、各所から参照する。

## 実装順序と検証

| Phase | 内容 | 目安 |
|---|---|---|
| P1 | migration一式（ビュー・self-only化・ブロック全面遮断・距離帯域化+ジッター+更新制限・reviewed_by・バケット非公開+審査テーブル） + psql/REST攻撃再現テスト | 大 |
| P2 | クライアント適応（profiles_public切替・年齢絞り込み・相性再正規化・署名URL表示・写真パス移行） | 大 |
| P3 | admin Basic認証 + 写真審査ページ + env必須化 + likeのNGワード | 中 |
| P4 | E2E（三点測位の再現不能確認・ブロック遮断・写真承認フロー）・受け入れ記録・レビュアーへの返信 | 中 |

**受け入れ条件（攻撃の再現テストで合格を判定）**:
1. 位置を3回変えて同一相手を測距しても、得られる距離から自宅圏（1km台）を特定できない（帯域+固定ジッターの実測）
2. 位置更新を31分以内に2回行うと2回目が拒否される
3. ブロック相手へのメッセージ/通話記録/デート相談がDB層で拒否される
4. 他人の birth_date・子ども情報・subscription_active がどのAPI経路でも取得できない
5. 認証ヘッダなしで admin のページ/Server Action にアクセスすると401
6. 未承認写真が本人以外に表示されない・管理画面で承認すると表示される
7. 既存の全機能E2E（検索〜いいね〜チャット〜デート〜通話〜課金）が引き続き動く
